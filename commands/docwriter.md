# ドキュメントの書き直し（Rust）

**対象範囲**: $ARGUMENTS（未指定なら `git diff HEAD` で変更を含む関数・型・impl）

既存コメントはコードの変更に追従していないことが多く、信用できない。対象範囲のコメントは消すのを既定とし、今のコードだけを根拠に書き直す。触るのはコメントと doctest だけで、コードは変更しない。

コメントは書いた分だけ、コードとずれる負債になる。書くのは、無いと読み手が誤る箇所だけにする。読み手は、API を呼ぶ人と、コードを変更する人（agent を含む）の両方。

## 事実と判断

書く内容は、コードから確かめられる事実と、コードからは読めない判断に分かれる。

**事実**は、panic やエラーの条件、不変条件、`unsafe` が健全である根拠など。挙動は文章ではなく doctest で示す。doctest は実行されるので、コードとずれれば壊れて気づける。

**判断**は、なぜその設計を選んだか、なぜそのリスクを許容したか、外部仕様をどう回避しているか。これが消えると、変更する人は意図的な判断を欠陥と見て「直して」しまう。だから判断は、制約だけでなく理由まで書く。不変条件を持つ型の `DerefMut` 実装に「`std::mem::replace` で差し替えると不変条件が崩れる」という注意だけがあると、読み手は実装自体を欠陥と見て消しかねない。「そうした呼び出しは現実的に起きないので、利便性を優先して許容している」まであって初めて正しく判断できる。

判断の出どころは、前提を確かめた既存コメントか、ユーザーの回答だけにする。推測は書かない。コメントはもっとも信用される位置にあるので、推測はもっともらしい誤りとしてそのまま信じられる。

どちらも今のコードについて現在形で書く。「Vec ではなく SmallVec を使う: 要素数はほぼ常に 4 以下で、ヒープ確保を避けたい」は理由が今のコードについて述べているので書いてよい。「以前は Vec だったが SmallVec に変えた」のような経緯（以前の姿、変更の経過、旧 API との差分、AI との会話で決めたこと）は書かない。

置き場所は、読み手が誤る場所の直近にする（`DerefMut` の例なら `impl` ブロック）。呼ぶ人が知るべき契約は `///`、変更する人だけが知ればよい判断は `//` に書く。

## 1. 振り分ける

対象範囲の既存コメントを一つずつ、次のうち最初に当てはまるものに振り分ける。判断の前提のうちコードベースで確かめられるもの（「`mem::replace` はどこからも呼ばれない」など）は、Grep などで確かめてから振り分ける。

1. 今のコードと食い違う事実・判断（前提が崩れた判断を含む）: **食い違い**
2. 経緯、事実、無くても読み手が誤らない判断: 消す。必要な事実は手順 3 で今のコードから書く
3. 理由まで揃い、前提が成り立つ判断: 残す
4. 理由が無いか曖昧な判断: **質問**

コメントが無くても、欠陥に見えるため「直される」おそれのある意図的な選択（`DerefMut` の例など）は**質問**にする。

対象範囲の既存コメントと意図的な選択をすべて振り分け終えてから、次に進む。

## 2. 質問する

質問があれば、すべてまとめて本文で聞き、ターンを終えて回答を待つ。回答次第で何を消し何を書くかが変わるので、回答を得るまでファイルは編集しない。各質問には、該当箇所のコード、読み取れた範囲の推測（あれば）、「なぜ許容しているのか」「変えてはいけない理由は何か」といった問いを添える。推測があれば、ユーザーは肯定か訂正だけで答えられる。

質問が無ければ聞かずに進む。

## 3. 書き直す

振り分けと回答に従って書き直す。残す判断も原文の文面は引き継がず、今のコードに合わせて書く。回答が「特に意図はない」なら何も書かない。食い違いの箇所は、どちらが正しいか決めつけられないので、その挙動については書かない。

最後に `cargo test --doc` が通ることを確認する。

## 4. 報告する

次を簡潔にまとめる。

- 消したもの
- 残した判断（原文と新しい文面を並べる）
- 書いたもの
- `cargo test --doc` の結果
- 食い違い: 原文とコードの挙動を並べ、`/thought-bug` での調査を提案する。なければ「なし」
