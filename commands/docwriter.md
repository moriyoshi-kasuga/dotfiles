# ドキュメントの書き直し（Rust）

**対象範囲**: $ARGUMENTS（未指定なら `git diff HEAD` の変更箇所）

既存のコメントはコードの変更に追従していないことが多く、信用できない。対象範囲のコメントはいったんすべて消し、今のコードだけを見て必要なものを書き直す。コードそのものは変更しない。

コメントは書いた分だけ、将来コードとずれる負債になる。コードを読めば分かることは書かず、読む人が本当に困る箇所にだけ書く。挙動を説明したくなったら、まず doctest で示せないか考える。doctest は実行されるので、コードとずれれば壊れて気づける。

## 経緯は書かない

読む人が見るのは今のコードだけで、それが書かれた経緯は知らないし、知る必要もない。そのため、時系列の語り（「以前は A だった」「B に変更した」、AI との会話で決めたこと）、旧 API や以前の実装との差分、変更履歴は書かない。既存コメントにこうした記述があれば、それも消す対象になる。

## 設計意図は残す

ただし、今のコードが持つ制約や、トレードオフを検討したうえで許容したリスクは経緯ではない。これが消えると、次にコードを触る人（agent を含む）が意図的な判断を欠陥と誤認して「直して」しまう。たとえば不変条件を持つ型に `DerefMut` を実装していて、「`std::mem::replace` で差し替えると不変条件が崩れる」という注意だけが残っていると、読み手は `DerefMut` の実装自体を危険と判断しかねない。「そうした呼び出しは現実的に起きないので、利便性を優先して許容している」という理由まで書いてあって、初めて正しく判断できる。

既存コメントの記述は、次の二段で判定する。

1. このコメントが無いと、将来の読み手が意図的な判断を欠陥と誤認したり、変更の是非を誤ったりするか。誤らないなら消す
2. 誤るなら、「制約・不変条件・許容したリスク」と「その理由」が揃っているかを見る。揃っていれば残す候補にし、揃っていなければ要検討にする

外部仕様の制約や回避策の理由も、この判定で扱う。

残す候補の前提のうち、コードベースで確かめられるもの（「`mem::replace` はどこからも呼ばれない」など）は Grep などで確かめる。前提が成り立てば、今のコードに合わせて書き直して残す。原文の文面は引き継がない。前提が崩れていれば残さず、コードと食い違う記述として扱う。古くなったトレードオフ判断は、残すとかえって誤判断を招く。

設計意図は、今のコードについての制約と理由として現在形で書く。「Vec ではなく SmallVec を使う: 要素数はほぼ常に 4 以下で、ヒープ確保を避けたい」は理由が今のコードについて述べているので書いてよい。「以前は Vec だったが SmallVec に変えた」は経緯なので書かない。境界は「A ではなく B」という文の形ではなく、理由が今のコードについて述べているかで引く。

置き場所は、誤判断が起きる場所（`DerefMut` の例なら `impl` ブロック）の直近にする。API の利用者が知るべき契約は `///`、実装者だけが知ればよい判断は `//` に書く。

## 要検討はまとめて聞く

次のものは推測で書かず、要検討にする。

- 判定 1 は通るが、理由が書かれていない、または曖昧な既存コメント
- 既存コメントは無いが、コードが明らかに意図的な選択をしている箇所（不変条件を持つ型の `DerefMut` 実装など）。意図はコードから読み取れないので、推測で書くと、もっとも信用される位置にもっともらしい誤りが入る

要検討はすべて洗い出してから、コメントを書く前にまとめて本文で質問し、ターンを終えて回答を待つ。各質問には、該当箇所のコード、読み取れた範囲の推測（あれば）、「なぜ許容しているのか」「変えてはいけない理由は何か」といった問いを添える。推測があれば、ユーザーは肯定か訂正だけで答えられる。回答をもとに設計意図を書き、回答が「特に意図はない」ならそのコメントは書かない。要検討がなければ質問せずに進める。

## コードと食い違う記述

コードの挙動と食い違う既存の記述（前提が崩れた設計意図を含む）は、不具合の可能性がある。どちらが正しいかを決めつけず、報告の要確認に原文を挙げ、`/thought-bug` での調査を提案する。

## 仕上げ

最後に `cargo test --doc` が通ることを確認する。

報告では、消したもの・残した設計意図（原文と新しい文面を並べる）・書いたもの・検証結果・要確認（なければ「なし」）を簡潔にまとめる。
