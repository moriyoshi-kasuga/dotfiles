# rethink

対象: $ARGUMENTS

ユーザーの困りごとや要望を、根幹の意図から考え直して最善案を確定させる。責務は最善案の確定まで。実装には入らない。

想定する場面は、勢いで（特にAIが）書いたコードを後から見直して「この実装はひどい」「このAPIはもう少し考え直したい」と感じたとき。

## マインド

- **要望は手段**: 「重複を消して」「凝集度を高めて」は手段で、その奥に本当に解きたい問題がある（XY問題）。要望を全箇所に一律に当てはめず、箇所ごとにそれが意図に効くかを判断する。効かない箇所は残し、残す理由を案に添える。重複を並べておいたほうが対応関係が見えるときのように、要望どおりにすると悪くなる箇所もあるため。
- **ゼロから書くなら**: 今のコードの構造・命名・コメントは勢いで書かれたもので、正解とは限らない。今ゼロから書くならどうするかを起点に考える。
- **理想から削る**: 枠の中での理想形をまず描き、大きすぎるなら「何を諦めればどこまで小さくなるか」の自然な切れ目で削る。小さい案から積み上げると、理想が見えないまま妥協してしまうため。

## 枠

ユーザーが決める枠は2種類ある。

- **制約**: 触ってはいけないところ（pubのAPIの形は変えない、など）
- **焦点**: 見る範囲（時間処理系だけ、IO処理系だけ、など）

枠が案を大きく縛っているなら、外せば何が良くなるかを一言添える（「pub API を変えてよければ、呼び出し側の変換が全部消える」など）。外すかどうかはユーザーが決め、外すなら1に戻って枠を決め直す。

## 進め方

1. **意図を掘る**: まずコードを読み、読めば分かることは聞かない。頭の中で案を組み立てながら、`grilling` skill で、答えによって案が変わる分岐点を聞く（根幹の意図、何を優先するか、枠）。案の方向が1つに定まったら次へ進む。
2. **ざっと見せる**: 推奨案を、方針とそれが根幹の意図をどう満たすか、変更後の公開APIのシグネチャ、呼び出し側コードの before/after で示す。理想から削った案があれば並べ、それぞれ何を諦めたかを添える。意図を推測で補った部分があれば明示する。
3. **フィードバックを受ける**: 方向が違えば1に戻る。細部を詰める必要があれば、そこで `grilling` を使って詰める。
4. **確定案をまとめる**: 方針、before/after、ざっくりしたdiff、破壊的変更の有無と影響範囲、移行コストをまとめ、実装に進むかを一言確認して終える。
