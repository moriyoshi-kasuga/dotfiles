# ブラッシュアップ

**対象**: $ARGUMENTS（未指定なら直前の作業対象か `git diff HEAD`）

まずフェーズ1で書き込みをせず設計を提案し、ユーザーの承認（`accept`、論点ごとの差し替え、補足付き承認など）を待ってからフェーズ2で書き込む。異論・懸念が来たらフェーズ1をやり直す。

**refactorは処理を完全に保ったまま見た目だけ変える。brushupは非公開実装なら処理内容自体を改善してよい。** 公開シグネチャ・型・入出力・副作用・エラー条件・パニック条件は基本的に保ち、既存テストは無修正でgreenになる前提。非公開の関数・型・モジュール内部構成・アルゴリズムは公開面を保つ範囲で自由に書き直してよい（DRY・KISS・YAGNI、凝集度と定義順序の一貫性、公開/非公開境界の見直し、コメントの鮮度）。

磨く過程で観測可能な振る舞い自体がその場しのぎ・バグ・一貫性のない仕様だと気づいたら、黙って直さず・黙って見逃さず、設計判断ポイントとして提案する（brushupの契約を超える変更を確定案に紛れ込ませない）。振る舞いを変える案を採用した場合のみ、その振る舞いを検証するテストを修正してよい。

## 出力

**フェーズ1（提案）**: 公開面（変えないもの）/ 非公開実装の問題点（`ファイル名:行番号` 根拠、DRY/KISS/YAGNI/凝集度/公開境界/コメント鮮度のどれか）/ ブラッシュアップ後の内部設計 / 設計判断ポイント（振る舞いを変える提案は推奨が明確でも必ずここに出す）/ `Grep` による影響確認。推奨は「最良の非公開実装」基準（振る舞いを変える論点だけは呼び出し側にとっての妥当性基準）。

**フェーズ2（実行）**: 採用方針の復唱 / 磨いたもの / 振る舞いの変更（採用した場合のみ、追従したテスト）/ 既存のビルド・lint・テストでの検証結果 / 要確認事項。
