# バグ原因特定

**症状**: $ARGUMENTS（未指定なら直前の会話のエラーログ等）

コードは変更しない。観察のためのコマンド実行はよい。

## 進め方

まず症状を1文にまとめ、考えられる原因を3つ以上挙げる。最初から1つに決め打ちすると、それを裏付ける観察ばかり選んでしまい、本当の原因を見落とすため。

各仮説について、それを反証できる最も安い観察を決める。1つの観察で複数の仮説を判定できるなら、それを優先する。

観察のコストは3段階で考える。

- **読むだけ**: Read・Glob・Grep、git の log/diff/blame/show
- **手元ですぐ終わる**: `cargo check`、フィルタで1本に絞ったテスト、hexdump など
- **重い**: ネットワーク操作（外部 API、依存の取得、DB 接続など）、フィルタなしの `cargo test`、`cargo run`、実行時間が見積もれないもの、副作用があるもの、ユーザーの環境や操作が必要なもの

読むだけ・手元ですぐ終わる観察は、安い順に上限なく実行して仮説を確定・除外していく。途中で分かった事実から新しい仮説が出てきたら追加してよい。

重い観察しか残らなくなったら、そこで止めて報告を出し、ユーザーの判断を待つ。重い観察は時間や副作用のコストがかかるうえ、ユーザーのほうが安く答えを知っていることも多い（「その API は今落ちている」「CI でしか再現しない」など）。ただし症状に再現手順が明示されていれば、その手順は実行してよい。

原因が1つに絞れても、そこで終わらず「なぜそれが起きたか」をもう1-2段掘る（例: null チェック漏れ、なぜ漏れたか、型がそのケースを表現できていない）。表面の原因だけ直すと、同じ種類のバグが別の場所で再発するため。

## 報告

読み手が最初に知りたいのは「結局何が原因で、次に何をすればいいか」なので、結論を先頭に置く。調査の経過を時系列で並べることはしない。根拠は各項目の横に添える。

確認済みの事実と推測を混ぜない。「わかったこと」には実際に観察で確かめたものだけを書き、推測は「結論」か「残っている仮説」に書く。該当するものがないセクションは省く。

```
## 結論: <確定 | 暫定 | 不明>
最も可能性の高い原因を1-3文で。暫定なら、そう考える根拠と、何が確かめられれば確定するかも書く。

## わかったこと
- <事実>（根拠: `path:line`、または実行したコマンドと出力の要点）

## 除外した仮説
- <仮説>: <除外した根拠>

## 残っている仮説
| 仮説 | 確かめ方 | 必要なもの |
|------|----------|------------|
| ... | ... | ネットワーク操作 / 全テスト実行（見積もり時間）/ ユーザーからの再現手順 など |

## 原因の構造（確定したときのみ）
- 直接原因: ...
- 構造的原因: ...
- 同じ原因が波及しうる箇所: ...

## 次の一手
最も効果の高い次の観察を1つ。ユーザーに頼みたいこと（重い観察の実行許可、再現手順、環境の情報など）があれば明記する。
```
