# バグ調査

**症状**: $ARGUMENTS（未指定なら直前の会話のエラーログ等）

土台は調査。「直して」と頼まれていても、まず原因を調べ、その調査で得た知識から修正方針を決める。原因が分からないまま直すと、症状だけ消えて原因が残るため。

次の3段階で進める。各段階の終わりで報告し、ユーザーの返答を待つ。

1. **初回調査**: コードを変更せず、安い観察で原因を探す
2. **再調査**: 段階1で原因が確定しなかったとき、ユーザーの返答で広がった範囲で調べ直す
3. **修正**: 承認された修正方針どおりに直す

## 段階1: 初回調査

コードは変更しない。観察のためのコマンド実行はよい。

まず症状を1文にまとめ、考えられる原因を3つ以上挙げる。最初から1つに決め打ちすると、それを裏付ける観察ばかり選んでしまい、本当の原因を見落とすため。

各仮説について、それを反証できる最も安い観察を決める。1つの観察で複数の仮説を判定できるなら、それを優先する。読むだけ・手元ですぐ終わる観察（下の「観察のコスト」）は、安い順に上限なく実行して仮説を確定・除外していく。途中で分かった事実から新しい仮説が出てきたら追加してよい。

重い観察は実行せずに残す。重い観察は時間や副作用のコストがかかるうえ、ユーザーのほうが安く答えを知っていることも多い（「その API は今落ちている」「CI でしか再現しない」など）。ただし症状に再現手順が明示されていればその手順は実行してよく、ユーザーが最初から許可している観察も同様。

原因が1つに絞れたら、下の「原因の掘り下げ」をしてから修正方針を立てる。

原因が確定するか、重い観察しか残らなくなった時点で段階1を終え、報告する。

- 確定した: 修正方針を提案し、承認を求める。承認されたら段階3に進む
- 確定しなかった: 結論を暫定か不明として出し、再調査に必要なものを「次の一手」でユーザーに頼む。頼めるのは次の3つ
  - 重い観察の実行許可
  - ユーザーしか知り得ない情報（環境、再現条件、過去の経緯など）
  - 調査のためのコード変更の許可（ログの追加、再現テストの追加、仮の修正を当てて症状が消えるか試すなど）

## 段階2: 再調査

ユーザーの返答で許可された観察と得られた情報を加え、段階1と同じ進め方で調べ直す。許可されていない重い観察は引き続き残す。

コードは、調査のための変更が許可された場合だけ変更する。変更は調査に必要な範囲にとどめ、加えた変更はすべて報告に載せる。

原因が確定するか、許可された範囲の観察を尽くした時点で段階2を終え、報告する。

- 確定した: 修正方針を提案し、承認を求める。承認されたら段階3に進む
- 確定しなかった: 新たに分かった事実を踏まえて推測を更新する。次にどうするか（さらに調査するか、推測に基づいて直すか、打ち切るか）はユーザーが決める。さらに調査するなら、新しい返答を受けて段階2を繰り返す

## 段階3: 修正

承認された修正方針どおりにコードを変更する。方針から外れる必要が出てきたら、修正を止めて方針を提案し直す。

段階2で調査のために加えた変更は、方針に含まれるもの（再現テストなど）以外は戻す。

修正後、最初に症状を確かめたのと同じ観察で、症状が消えたことを確認する。その観察が重いなら、実行前に許可を取る。

## 観察のコスト

観察のコストは3段階で考える。

- **読むだけ**: Read・Glob・Grep、git の log/diff/blame/show
- **手元ですぐ終わる**: 型検査や評価だけのコマンド（`cargo check`、`nix eval` など）、フィルタで1本に絞ったテスト、hexdump など
- **重い**: ネットワーク操作（外部 API、依存の取得、DB 接続など）、フィルタなしのテスト全体、プログラムの実行やシステム全体のビルド（`cargo run`、`nixos-rebuild` など）、実行時間が見積もれないもの、副作用があるもの、ユーザーの環境や操作が必要なもの

## 原因の掘り下げ

原因が1つに絞れても、そこで終わらず「なぜそれが起きたか」をもう1-2段掘る（例: null チェック漏れ、なぜ漏れたか、型がそのケースを表現できていない）。表面の原因だけ直すと、同じ種類のバグが別の場所で再発するため。

## 報告

段階1・2の終わりに、次の形式で報告する。

読み手が最初に知りたいのは「結局何が原因で、次に何をすればいいか」なので、結論を先頭に置く。調査の経過を時系列で並べることはしない。根拠は各項目の横に添える。

確認済みの事実と推測を混ぜない。「わかったこと」には実際に観察で確かめたものだけを書き、推測は「結論」か「残っている仮説」に書く。該当するものがないセクションは省く。

```
## 結論: <確定 | 暫定 | 不明>
最も可能性の高い原因を1-3文で。暫定なら、そう考える根拠と、何が確かめられれば確定するかも書く。

## わかったこと
- <事実>（根拠: `path:line`、または実行したコマンドと出力の要点）

## 除外した仮説
- <仮説>: <除外した根拠>

## 残っている仮説
| 仮説 | 確かめ方 | 必要なもの |
|------|----------|------------|
| ... | ... | ネットワーク操作 / 全テスト実行（見積もり時間）/ ユーザーからの情報 / 調査用のコード変更 など |

## 調査用に加えた変更（段階2で変更したときのみ）
- `path:line`: 何を確かめるために何を加えたか

## 原因の構造（確定したときのみ）
- 直接原因: ...
- 構造的原因: ...
- 同じ原因が波及しうる箇所: ...

## 修正方針（確定したときのみ）
直接原因と構造的原因のどこまでを、どう直すか。変更箇所（`path:line`）、影響範囲、修正後に症状が消えたことを確かめる方法も書く。規模の違う案が複数あるなら、それぞれを示して推奨を1つ添える。

## 次の一手
確定したなら、修正方針の承認を求める。確定していないなら、最も効果の高い次の観察を1つと、ユーザーに頼みたいことを書く。段階2で確定しなかったなら、取りうる選択肢を並べてユーザーの判断を仰ぐ。
```
