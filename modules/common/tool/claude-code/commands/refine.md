# 公開APIの洗練（Rust）

**対象**: $ARGUMENTS

> - **パス・箇所指定あり**: それを対象にする（説明文の場合は `Glob`/`Grep` で特定してから対象を提案冒頭で明示する）
> - **未指定**: 直前の作業対象または `git diff HEAD` を対象にする。差分が複数の無関係な変更にまたがる場合は範囲を先に確認する

## 哲学

**設計思想は正しい。触り心地だけが悪い。** その前提に立ち、思想を一切動かさずに公開APIの使い勝手だけを改善する。

- **思想は不可侵** — 責務分割（どの型が何を持つか）、不変条件（何を常に保証しているか）、依存の向き・レイヤリング、同期/非同期や所有/借用の基本方針、そして「意図的にやらないと決めていること」は変えない。これらを変えたくなった時点で refine の範囲外であり、`/rewrite` の領分
- **使い勝手は呼び出し側にしか現れない** — 「このAPIは使いにくい」は宣言型のソースを眺めても分からない。実際の呼び出し箇所に繰り返し現れるボイラープレート、取り違えやすい引数、毎回書かされる変換こそが証拠になる。診断は必ず利用箇所の実地調査から始める
- **破壊的変更は手段として許容する** — 後方互換のために使いにくさを温存しない。壊れる利用箇所はこちらで追従修正する。ただし変更は「使いやすさのために必要な分だけ」であり、ついでの再設計はしない
- **内部実装の磨き上げは目的にしない** — 公開面を変えた結果として必要になる内部の追従だけを行う。それ以上の重複解消・アロケーション削減・定義順序の整理は `/brushup` に委ねる。スコープを混ぜると、何が使い勝手の改善だったのか diff から読めなくなる
- **コードそのものが仕様書である** — 型・命名・構造で表現できることはそちらで表現し、ドキュメント・コメントは最後の手段にする

### このスキルを使うべきでない場合

診断の過程で次が判明したら、フェーズ2に進まずその旨を伝えて中断する。無理に refine の枠に押し込むと、思想を密かに書き換えた中途半端な変更になる。

- **思想そのものが使いにくさの原因** — 責務分割や不変条件の置き方が間違っており、公開面をどう整えても呼び出し側が楽にならない → `/rewrite` を勧める
- **公開面に問題がない** — 使いにくさの正体が内部実装の遅さ・読みにくさだった → `/brushup` を勧める

## 実行手順

このスキルは **2フェーズ** で進める。フェーズ1の提案が accept されるまで、ファイルへの書き込みは行わない。

### フェーズ1: refine 設計の提案（accept 待ち）

1. **思想の言語化** — 対象コードを読み、責務分割・不変条件・依存の向き・基本方針・意図的な非対応を言語化する。これが「変えてはいけない軸」になる。ここで思想自体の破綻に気づいたら「このスキルを使うべきでない場合」に従う
2. **公開面の棚卸し** — `pub` なシグネチャ・型・フィールド・モジュール公開経路・実装済みの標準トレイトを一覧にする。改善の対象範囲であり、同時に破壊的変更の全量でもある
3. **呼び出し側の実地調査** — `Grep` で利用箇所を集め、実際のコードを読む。繰り返し現れる変換（`.to_string()`/`.clone()`/`.collect()`）、意味の読めない引数（bool リテラル・同型の連続引数）、毎回書かれる定型の前処理・後処理、エラーハンドリングの不自然さを具体的に拾う。**利用箇所が存在しない場合**は、そのAPIが想定する代表的な利用シナリオを自分で書き起こして代用する（その旨を提案に明記する）
4. **使いにくさの診断** — 3で拾った事実を「使いにくさの観点」（後述）に対応づけ、それぞれ何が呼び出し側の負担になっているかを述べる。観点の名前だけを並べず、必ず実コードを根拠にする
5. **改善後の公開APIの提示** — 新しいシグネチャ・型・トレイト実装・公開経路を示し、**それぞれが1で言語化した思想のどれを保っているか**を対応づける。一意に定まる部分は確定案として書く
6. **呼び出し側 Before/After** — 3で拾った実際の利用箇所を使い、変更前後の呼び出しコードを並べる。使いやすくなったことの唯一の客観的な証拠であり、ここで差が出ない変更は提案から落とす
7. **設計判断ポイントの抽出** — 合理的な選択肢が複数あり判断が分かれる箇所を番号付きで列挙し（詳細は「出力形式」）、各論点に方針 A/B/C とメリット・デメリット・推奨案を添える
8. **破壊的変更と影響範囲の明示** — 変わるAPIごとに移行方法を示し、`Grep` で確認した壊れる利用箇所を列挙する

ここで提案を出し、**ユーザーの判断を待つ**。設計の方向性が固まるまでは実装に着手しない。

### フェーズ2: refine 実行（accept / 方針指定 後）

**入力形式（定型）**

| 入力 | 意味 |
|---|---|
| `accept` | 全設計判断ポイントで **推奨案** を採用する |
| `1=A,2=C` | 論点1は A、論点2は C を採用。**指定のない論点は推奨案** を採用する |
| `accept` + 補足文 | 推奨案ベースに、補足文の指示を上書きで反映する |
| 上記以外（設計そのものへの異論・追加要望・懸念） | フェーズ2には進まない。診断・新API設計にフィードバックを反映し、フェーズ1の提案をやり直す |

**実行手順**

9. **採用方針の確定** — 入力を上記の形式で解釈し、各論点で採用する方針を1行で復唱する（例: `論点1=A（推奨） / 論点2=C`）
10. **公開APIの変更** — 確定した設計で公開面を書き換える。内部実装は新しい公開面を成立させるのに必要な範囲だけ追従させる
11. **利用箇所の追従** — 破壊的変更で壊れる呼び出し元を、新APIに合わせて修正する。ここが Before/After で示した After そのものになっているかを確認する
12. **検証** — `cargo check` → `cargo clippy` → `cargo test` の順に実行して green にし、最後に `cargo fmt` を実行する。既存テストが旧APIに依存して壊れる場合は、テストの意図（＝検証している振る舞い）は維持したまま新APIに沿って書き直す。doctest も公開APIの一部なので更新する

## 使いにくさの観点（Rust）

診断と改善の共通言語として使う。すべてを機械的に適用するのではなく、3で拾った実コードに該当するものだけを扱う。

### 引数

- 呼び出し側が毎回書いている変換は、境界を緩めて消せる: `String` → `impl Into<String>`、`&Path`/`&str` → `impl AsRef<Path>`/`AsRef<str>`、`Vec<T>`/`&[T]` → `impl IntoIterator<Item = T>`
- 意味の読めない引数を型にする: bool 引数は二値の enum に、同型の連続引数（`fn new(width: u32, height: u32)` を取り違える類）は newtype に。呼び出し箇所を読んで意味が分かる状態を目指す
- 引数が多い場合、必須が少なく任意が多いなら builder、フラットな設定の塊なら `Default` を実装した option struct。どちらも呼び出し側の記述量が減らないなら導入しない
- **ジェネリクスの入れすぎは逆効果** — 型推論が効かず turbofish を強いる、エラーメッセージが読めなくなる、object safety を失って `dyn` にできなくなる、単相化でコードが膨らむ。緩めた境界がこれらを招くなら具体型のままにする

### 返り値

- 中間 `Vec` を挟んでいるなら `impl Iterator<Item = T>` を検討する。ただし呼び出し側の大半が結局 `collect()` するなら `Vec` のままが素直
- 無名タプルの返り値は要素の意味が呼び出し側に伝わらない。名前付き struct にする
- `Option<Result<T, E>>` と `Result<Option<T>, E>` は、呼び出し側が実際に分岐したい順序に合わせる
- 捨てると意味のない返り値には `#[must_use]` を付ける

### エラー

- **呼び出し側が分岐したい単位で variant を切る** — 分岐に使われない区別は variant を分けず、メッセージや `source` に押し込む。逆に、呼び出し側が握り潰すしかない不透明なエラーは分解する
- ライブラリ境界なら `thiserror` + `#[non_exhaustive]`、アプリ境界なら `anyhow` のようにレイヤで使い分ける
- `Display` に「何をしようとして失敗したか」を含め、`source()` チェーンを切らない

### 命名（Rust API Guidelines に従う）

- `as_`（借用・ゼロコスト） / `to_`（コストあり） / `into_`（所有権を消費）を使い分ける
- getter に `get_` を付けない、setter は `set_`
- イテレータは `iter` / `iter_mut` / `into_iter`、コレクション型には `IntoIterator`（`&T` 版も）を実装する
- 変換は `From`/`TryFrom`、文字列パースは `FromStr`（`"...".parse()` で呼べるようになる）
- 型名は名詞、メソッドは動詞。頭字語は `Uuid`/`HttpClient` のように先頭のみ大文字

### 標準トレイト実装

呼び出し側が「Rust として普通に書ける」ようにするための面。derive で済むものが未実装なら、それだけで使い勝手が落ちている。

- `Debug` は事実上必須。`Clone`/`Default`/`PartialEq`/`Eq`/`Hash`/`PartialOrd` は意味が通るなら derive する
- `From` で構築を短く、`Display` で表示、`FromStr` でパース、`Extend`/`FromIterator` でコレクション操作を可能にする
- `Deref` を継承もどきに使わない。newtype がスマートポインタ的である場合に限る
- `Send`/`Sync`/`'static` が付くべき型に付いているかを、実際の利用文脈（スレッド跨ぎ・async タスク）から確認する

### 発見しやすさ・モジュール公開

- 階層が深い型は `pub use` で再エクスポートし、「1つの正しい import 経路」を作る
- 実装詳細のはずの型が公開シグネチャに漏れていないか（＝`cargo doc` に出てしまうか）を確認する
- 将来の追加に備える `#[non_exhaustive]`、公開フィールドを避けてアクセサに寄せる判断は、思想を変えない範囲で行う

### 誤用しにくさ

- 呼び忘れると壊れる init/cleanup は RAII（`Drop`）に寄せる
- 呼び出し順序への依存は、型で順序を強制できないか検討する。ただし typestate の導入がアーキテクチャの作り直しになるなら、それは refine ではなく `/rewrite` の領分

## コメント方針

コメントは書いた瞬間からコードと乖離するリスクを負う「負債」である。公開APIを変えると既存の doc コメントは高確率で嘘になるため、変更した公開面の doc は必ず点検する。

- **WHAT/HOW は書かず、WHY だけ残す** — コードを読めばわかることは削除し、変数名・関数名で表現しきれない非自明な理由（隠れた制約・仕様上の理由・不具合への回避策など）だけを、リポジトリ内の情報だけで理解できる形で残す
- **会話・一時情報・自明なイディオムへの言及は禁止** — ユーザーとのやり取りの引き写し、Issue番号など陳腐化する外部参照、`UnsafeCell` の `Send`/`Sync` 手動実装のような標準的イディオムへの説明は書かない
- **詳細仕様は doctest に逃がす** — 引数や挙動の詳細は `# Examples` の動作可能な doctest で示し、陳腐化を防ぐ。refine では doctest が「新しいAPIがどれだけ短く書けるか」の実演も兼ねるため、Before/After の After をそのまま doctest にできることが多い
- **`// SAFETY:`** — `unsafe` で非自明な不変条件がある場合のみ要点を簡潔に書く（`transmute` の layout 保証なら `same layout` 程度で十分）
- **doc コメント（`///`/`//!`）は公開 API のみ** — `# Errors`/`# Panics`/`# Safety` は非自明な条件がある場合のみ設け、prose の箇条書きより doctest（`should_panic`、`Err` を返す例）での実演を優先する。他の型・関数への言及は `` [`Type`] `` で intra-doc link にする
- **英語のみでコメントする方針の場合は ASCII のみを使う** — em dash（—）や矢印（→ など）は使わず、文の区切りにはピリオドを使う

**改行（rustfmt はコメントを再整形しないため厳守）**: 1文は改行せず1行で書き、画面幅に合わせた機械的な折り返しは禁止。改行してよいのは箇条書き項目間・見出し前後・コードブロック前後、または150文字超の文を読点等の切れ目でやむを得ず区切る場合のみ。段落途中に無駄な空行を挟まない

````
## 設計判断ポイント
判断が分かれる箇所のみを列挙する。`accept` で全て推奨案を採用、個別指定は `1=A,2=C` 形式。

### 1. [論点のタイトル]
- **A（推奨）**: [案] — 利点: [...] / 欠点: [...]
- **B**: [案] — 利点: [...] / 欠点: [...]
- **C**: [案] — 利点: [...] / 欠点: [...]
- 推奨理由: [なぜ A を推すか。1〜2行]

### 2. [論点のタイトル]
- **A（推奨）**: ...
- **B**: ...

## 破壊的変更
- [変わる API / シグネチャ / 公開経路] — 移行方法: [旧 → 新の対応]

## 影響範囲（壊れる利用箇所）
- `ファイル名:行番号` — [どう壊れるか・どう追従するか]
````

**設計判断ポイントの作り方**

- **論点ごとに1番号、独立させる** — 番号間で互いに依存しないようにする
- **選択肢は A から順に、A は必ず推奨案** — 案が2つなら A/B、3つなら A/B/C
- **推奨は「呼び出し側にとって最良」基準で選ぶ** — 移行コスト・変更量・既存への近さは推奨理由にせず、破壊的変更・影響範囲の欄で扱う
- **利点・欠点は具体的に** — 「柔軟」「安全」のような抽象語で終わらせず、呼び出し側のコードが何行減るか・何を間違えられなくなるかを書く
- **真に分かれるものだけ論点にする** — 推奨が明確で他案に意味がない場合は、改善後APIの確定案に含める
- **外部に公開されている crate で段階移行が要る場合**、旧APIを `#[deprecated]` で残すか一括削除するかは論点になりうる。リポジトリ内で利用箇所が完結しているなら論点にせず一括追従する

提案後、ユーザーの判断（`accept` または方針指定）を待つ。判断が来るまで実装しない。

### フェーズ2: refine 結果（accept / 方針指定 後）

- **採用方針**: 各論点で採用した方針の復唱（例: `論点1=A（推奨） / 論点2=C`）
- **変えた公開API**: 確定した設計での新しい公開面のコード
- **追従修正**: 破壊的変更に合わせて修正した利用箇所（提案の After 通りになっているか）
- **検証結果**: `cargo check` / `cargo clippy` / `cargo test`（doctest 含む） / `cargo fmt` の実行結果
- **要確認**: 自動検証で担保できない確認事項（外部利用者への影響・実行時の挙動変化など）。なければ「なし」
