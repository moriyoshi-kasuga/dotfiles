# 公開APIの洗練（Rust）

**対象**: $ARGUMENTS

対象の決め方・フェーズ運用・設計判断ポイントの書式は `rust-coder` スキルの「提案フェーズの共通ルール」に従う。

## 哲学

**設計思想は正しい。触り心地だけが悪い。**

- **思想は不可侵** — 責務分割（どの型が何を持つか）、不変条件、依存の向き・レイヤリング、同期/非同期や所有/借用の基本方針、「意図的にやらないと決めていること」は変えない
- **使い勝手は呼び出し側にしか現れない** — 宣言型のソースを眺めても使いにくさは分からない。呼び出し箇所に繰り返し現れるボイラープレート、取り違えやすい引数、毎回書かされる変換こそが証拠になる。診断は必ず利用箇所の実地調査から始める
- **破壊的変更は手段として許容する** — 後方互換のために使いにくさを温存しない。壊れる利用箇所はこちらで追従修正する。ただし変更は使いやすさのために必要な分だけで、ついでの再設計はしない
- **内部実装の磨き上げは目的にしない** — 公開面を変えた結果として必要になる内部の追従だけを行う。スコープを混ぜると、何が使い勝手の改善だったのか diff から読めなくなる

診断の過程で次が判明したら、フェーズ2に進まずその旨を伝えて中断する。無理に refine の枠に押し込むと、思想を密かに書き換えた中途半端な変更になる。

- 責務分割や不変条件の置き方自体が使いにくさの原因で、公開面をどう整えても呼び出し側が楽にならない → `/rewrite` を勧める
- 使いにくさの正体が内部実装の遅さ・読みにくさだった → `/brushup` を勧める

## 実行手順

### フェーズ1: refine 設計の提案

0. `Skill(rust-coder)` を読み込む
1. **保つ思想の言語化** — 責務分割・不変条件・依存の向き・基本方針・意図的な非対応を言語化する。これが「変えてはいけない軸」になる。ここで思想自体の破綻に気づいたら上記に従って中断する
2. **公開面の棚卸し** — `pub` なシグネチャ・型・フィールド・モジュール公開経路・実装済みの標準トレイトを一覧にする。改善の対象範囲であり、同時に破壊的変更の全量でもある
3. **呼び出し側の実地調査** — `Grep` で利用箇所を集めて実際のコードを読み、繰り返し現れる変換（`.to_string()`/`.clone()`/`.collect()`）、意味の読めない引数（bool リテラル・同型の連続引数）、毎回書かれる定型の前処理・後処理、エラーハンドリングの不自然さを具体的に拾う。利用箇所が存在しない場合は代表的な利用シナリオを自分で書き起こして代用し、その旨を提案に明記する
4. **使いにくさの診断** — 3で拾った事実を「使いにくさの観点」に対応づける。観点の名前だけを並べず、必ず実コードを根拠にする
5. **改善後の公開API** — 新しいシグネチャ・型・トレイト実装・公開経路を示し、それぞれが1の思想のどれを保っているかを対応づける。一意に定まる部分は確定案として書く
6. **呼び出し側 Before/After** — 3で拾った実際の利用箇所で変更前後を並べる。使いやすくなったことの唯一の客観的な証拠であり、ここで差が出ない変更は提案から落とす
7. **設計判断ポイント** — 判断が分かれる箇所を列挙する
8. **破壊的変更と影響範囲** — 変わるAPIごとに移行方法を示し、`Grep` で確認した壊れる利用箇所を列挙する

### フェーズ2: refine 実行

9. 採用方針を復唱し、確定した設計で公開面を書き換える。内部実装は新しい公開面を成立させるのに必要な範囲だけ追従させる
10. 壊れる呼び出し元を新APIに合わせて修正し、Before/After で示した After そのものになっているか確認する
11. `rust-coder` の検証手順で green にする。旧APIに依存して壊れる既存テストは、検証している振る舞いを維持したまま新APIに沿って書き直す。doctest も公開APIの一部なので更新する

## 使いにくさの観点（Rust）

診断と改善の共通言語として使う。機械的に全て適用せず、3で拾った実コードに該当するものだけを扱う。

### 引数

- 呼び出し側が毎回書いている変換は境界を緩めて消せる: `String` → `impl Into<String>`、`&Path`/`&str` → `impl AsRef<Path>`/`AsRef<str>`、`Vec<T>`/`&[T]` → `impl IntoIterator<Item = T>`
- 意味の読めない引数を型にする。bool 引数は二値の enum に、同型の連続引数（`fn new(width: u32, height: u32)` を取り違える類）は newtype に
- 引数が多い場合、必須が少なく任意が多いなら builder、フラットな設定の塊なら `Default` を実装した option struct。どちらも呼び出し側の記述量が減らないなら導入しない
- ジェネリクスの入れすぎは逆効果。型推論が効かず turbofish を強いる、エラーメッセージが読めない、object safety を失って `dyn` にできない、単相化でコードが膨らむ。緩めた境界がこれらを招くなら具体型のままにする

### 返り値

- 中間 `Vec` を挟んでいるなら `impl Iterator<Item = T>` を検討する。ただし呼び出し側の大半が結局 `collect()` するなら `Vec` のままが素直
- 無名タプルは要素の意味が呼び出し側に伝わらないので、名前付き struct にする
- `Option<Result<T, E>>` と `Result<Option<T>, E>` は、呼び出し側が実際に分岐したい順序に合わせる

### エラー

- 呼び出し側が分岐したい単位で variant を切る。分岐に使われない区別は variant を分けずメッセージや `source` に押し込み、逆に握り潰すしかない不透明なエラーは分解する
- ライブラリ境界なら `thiserror`、アプリ境界なら `anyhow` のようにレイヤで使い分ける
- `Display` に「何をしようとして失敗したか」を含め、`source()` チェーンを切らない

### 命名

Rust API Guidelines に従う。特に `as_`（借用・ゼロコスト） / `to_`（コストあり） / `into_`（所有権を消費）の使い分け、イテレータの `iter` / `iter_mut` / `into_iter`、変換の `From`/`TryFrom`、文字列パースの `FromStr`（`"...".parse()` で呼べるようになる）を確認する。

### 標準トレイト実装

derive で済むものが未実装なら、それだけで「Rust として普通に書ける」性質が落ちている。`Debug` は事実上必須、`Clone`/`Default`/`PartialEq`/`Eq`/`Hash`/`PartialOrd` は意味が通るなら derive する。`From` で構築を短く、`Display` で表示、`FromStr` でパース、`Extend`/`FromIterator`・`IntoIterator`（`&T` 版も）でコレクション操作を可能にする。`Deref` は newtype がスマートポインタ的である場合に限り、継承もどきには使わない。`Send`/`Sync`/`'static` が付くべき型に付いているかを、実際の利用文脈（スレッド跨ぎ・async タスク）から確認する。

### 発見しやすさ・誤用しにくさ

- 階層が深い型は `pub use` で再エクスポートし、「1つの正しい import 経路」を作る
- 実装詳細のはずの型が公開シグネチャに漏れていないか（＝`cargo doc` に出てしまうか）を確認する。公開フィールドを避けてアクセサに寄せる判断は、思想を変えない範囲で行う
- 呼び忘れると壊れる init/cleanup は RAII（`Drop`）に寄せる
- 呼び出し順序への依存は型で強制できないか検討する。ただし typestate の導入がアーキテクチャの作り直しになるなら `/rewrite` の領分

## コメント方針

`rust-coder` スキルのコメント方針に従う。公開APIを変えると既存の doc コメントは高確率で嘘になるため、変更した公開面の doc は必ず点検する。Before/After の After はそのまま doctest にできることが多い。

## 出力形式

### フェーズ1: 提案

````
## 保つ思想
## 現在の公開API
## 使いにくさの診断
[`ファイル名:行番号` の実コードを根拠にする]

## 改善後の公開API
[各変更が「保つ思想」のどれを保っているかの対応づけも書く]

## 呼び出し側 Before / After
### `ファイル名:行番号`
```rust
// Before
...
```
```rust
// After
...
```
[何が減った/読めるようになった/間違えられなくなったか。1行]

## 設計判断ポイント
## 破壊的変更
- [変わる API / シグネチャ / 公開経路] — 移行方法: [旧 → 新の対応]

## 影響範囲（壊れる利用箇所）
- `ファイル名:行番号` — [どう壊れるか・どう追従するか]
````

推奨は「呼び出し側にとって最良」基準で選び、利点・欠点には呼び出し側のコードが何行減るか・何を間違えられなくなるかを書く。外部に公開されている crate で段階移行が要る場合、旧APIを `#[deprecated]` で残すか一括削除するかは論点になりうるが、リポジトリ内で利用箇所が完結しているなら一括追従する。

### フェーズ2: refine 結果

**採用方針** / **変えた公開API** / **追従修正**（提案の After 通りになっているか） / **検証結果**（doctest 含む） / **要確認**（自動検証で担保できない確認事項。外部利用者への影響・実行時の挙動変化など。なければ「なし」）
