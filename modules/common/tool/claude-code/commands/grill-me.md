# 計画のグリル

**テーマ**: $ARGUMENTS

> - **具体的な計画・方針の指定**: それを叩き台にして詳細を詰める（例:「〇〇機能を△△という設計で追加したい」）
> - **困りごと・相談内容の指定**: それを起点に調査し、改善案を練る（例:「エラーハンドリングが場当たり的で辛い」「これはこうしたほうがいい気がする、どう思う？」）
> - **対象パスの指定**: そのディレクトリ・ファイルを調査の起点にする
> - **未指定**: 直前の会話コンテキストを起点にする

## 原則

- **実装・コード変更は行わない** — 論点をすり合わせ、決定事項をまとめるところまで。実装は `/impl-rust` 等に引き継ぐ
- **根本原因を論点にする** — 困りごとが起点のときは表面の症状ではなく根本原因を論点にする（例:「コメントが多すぎる」の裏に「命名が意図を表現できていない」があればそちらを論点にする）
- **決まっていない論点は推奨案を出す** — 選択肢を並べて判断を丸投げしない。最も良いと考える案を推奨にし、理由を添える。最終判断はユーザーに委ねる
- **事実と意見を区別する** — コードの現状は `ファイル名:行番号` で根拠を示し、価値判断と混ぜない

## 手順

1. まずコードベースを軽く調査し、方針が大きく変わりうる論点がないか確認する。あればAskUserQuestionでまとめて質問する。なければこのステップは飛ばしてよい。
2. その回答（または1を飛ばした場合はテーマそのもの）を踏まえて、詳細なコードベース調査を行う。論点ごとに関係するファイルを特定して読み、現状を `ファイル名:行番号` で押さえる。
3. 論点ごとに次のどちらかで扱う。
   - **方向性が決まっている論点**: その方向を前提に、決めなければ実装に進めない詳細（境界値・エラー時の挙動・依存先など）を詰める質問を作る
   - **方向性が決まっていない論点**: 調査結果をもとに解決案を2〜3案作り、最も良いと考える案に「(推奨)」を付ける
4. 論点をAskUserQuestionでまとめて質問する。**ただし、ある論点の回答次第で他の論点の前提や選択肢自体が変わってしまう（後戻りが起きる）場合は、その論点同士を同じ回にまとめない。** 依存元の論点だけを先に質問し、回答を踏まえて調査をやり直してから、依存先の論点を次の回で質問する。互いに独立していて、どちらの答えが出ても他方の前提が揺るがない論点だけをまとめてよい。選択肢を提示できる質問は必ずAskUserQuestionを使う。地の文での自由記述質問は、ユーザーの自由入力をもとに検討したい場合のみ使う。
5. 回答によってさらに調査すべき点や新たな論点が生じたら、2〜4を繰り返す。

コードベースを調査すれば答えが得られる質問であれば、質問する代わりにコードベースを調査すること。

調査の過程で、この計画・相談とは別に原因不明の既存バグを発見した場合は、その場で深追いせず `/thought-bug` の使用を提案する。

## 決定事項のまとめ

共通の認識に達したら、決定事項をMarkdownファイルにまとめて、claude-code起動時のカレントディレクトリ直下に書き出す。このファイル単体を渡せば別セッション・別コンテキストからでも作業に着手できるように、以下を含めること。

- 設計時刻: `date '+%Y-%m-%d %H:%M:%S'` を実行して取得した現在時刻を `yyyy-mm-dd HH:MM:SS` 形式でファイル冒頭に記載する
- 調査対象: 何についての調査・設計かを明記する
- 概要
- 結論
- 合意した設計・決定事項とその理由
- 実装に必要な調査結果・コンテキスト（根拠となった `ファイル名:行番号` を含む）
- 参照すべきファイル・パス
- 残っている未解決点（あれば）

さらに、この仕様書はあくまでtemporaryな一時的agent指示ファイルであることを明記する。多くの場合これはAIへの指示を目的としたものであり、ドキュメントやコードコメントで説明すべき内容ではないためである。また、記載した設計時刻から時間が経過している場合、実際の実装や仕様が本書の内容と異なっているケースがありうる旨も明記する。

Rustの実装に関する計画であれば、`/impl-rust` にそのまま渡せる仕様書として書く（実装方針・コメント方針は `rust-coder` スキルに準拠する前提で書く）。
