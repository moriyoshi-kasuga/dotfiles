# ブラッシュアップ（Rust）

**対象**: $ARGUMENTS

対象の決め方・フェーズ運用・設計判断ポイントの書式は `rust-coder` スキルの「提案フェーズの共通ルール」に従う。

## 哲学

**refactor は処理を完全に保ったままコードの見た目だけを変える。brushup は非公開実装であれば処理内容そのものを改善してよい。ただし公開 API・外部から観測可能な振る舞いは一切変えない。**

- **公開面は不可侵** — シグネチャ・公開型・公開モジュール構成・入出力・副作用・エラー条件・パニック条件を完全に保つ。既存テストは無修正で green になることが前提。テストが内部実装に依存していて壊れる場合は、そのテスト自体が実装詳細に踏み込みすぎている signal であり、brushup 側の設計不備ではない旨を提案時に指摘する
- **非公開実装は全面的な再設計の対象** — private な関数・構造体・モジュール内部構成・定義順序・アルゴリズムは、公開面を保つ範囲で自由に書き直してよい。より効率的なアルゴリズムへの差し替え、内部データ構造の変更も対象

## 実行手順

### フェーズ1: brushup 設計の提案

0. `Skill(rust-coder)` を読み込む
1. **公開面の確定** — 対象コードを読み、`pub` なシグネチャ・型・モジュール構成、および入出力・副作用・エラー条件・パニック条件など外部から観測可能な振る舞いを洗い出し、「変えてはいけない境界」を明示する
2. **非公開実装の問題点** — 重複コード、無駄な alloc、モジュール構成の乱れ、定義順序に一貫性がない箇所など、磨くべき点を具体的に挙げる
3. **ブラッシュアップ後の内部設計** — 公開面を変えずに実現する改善後の非公開実装を、関数分割・型設計・定義順序・モジュール構成で示す。一意に定まる部分は確定案として書く
4. **設計判断ポイント** — 判断が分かれる箇所を列挙する
5. **影響確認** — 公開面は変えない前提だが、`Grep` で実際の利用箇所を確認し、意図せず壊れる箇所がないことを裏付ける（あれば設計を見直す）

### フェーズ2: ブラッシュアップ実行

6. 採用方針を復唱し、公開面は一切変えずに確定した設計で非公開実装のみを書き直す
7. `rust-coder` の検証手順で green にする。既存テストは無修正で通ることが前提であり、通らない場合は公開面に踏み込んでいないか設計を見直す

## brushup 固有の観点

- 重複コードは関数化でまとめる（ジェネリクス・マクロでの共通化は関数化で不十分な場合の最終手段）
- 無駄な `clone()`/`to_vec()`/`collect()` を削減し、イテレータチェーンで中間アロケーションを排除する。所有権を持つ必要がない箇所は参照で済ませ、必要に応じて `Cow` を活用する
- 公開/非公開の境界を見直し、関連する型・関数を近接配置する。定義順序は一貫した基準（呼び出し関係・抽象度・関心事によるグルーピングなど）を持たせる
- 非公開ヘルパーは適切な粒度に分割・統合する（過度に細分化された関数はまとめ、肥大化した関数は責務ごとに分ける）
- 既存コメントが非公開実装の変更に追従できているかを磨き直しの段階で見直す

## 出力形式

### フェーズ1: 提案

```
## 公開面（変えないもの）
[pub なシグネチャ・型・モジュール構成、および外部から観測可能な入出力・副作用・エラー条件・パニック条件]

## 非公開実装の問題点
## ブラッシュアップ後の内部設計
## 設計判断ポイント
## 影響確認（利用箇所）
- `ファイル名:行番号` — [公開面が保たれていることの確認結果]
```

推奨は「最良の非公開実装」基準で選ぶ。

### フェーズ2: ブラッシュアップ結果

**採用方針** / **磨いたもの**（公開面は無変更） / **検証結果**（既存テスト無修正で green） / **要確認**（自動検証で担保できない確認事項。実行時の挙動・パフォーマンス特性の変化など。なければ「なし」）
