# ブラッシュアップ（Rust）

**対象**: $ARGUMENTS

> - **パス・箇所指定あり**: それを対象にする（説明文の場合は `Glob`/`Grep` で特定してから対象を提案冒頭で明示する）
> - **未指定**: 直前の作業対象または `git diff HEAD` を対象にする。差分が複数の無関係な変更にまたがる場合は範囲を先に確認する

## 哲学

**refactor は処理を完全に保ったままコードの見た目だけを変える。brushup は非公開実装であれば処理内容そのものを改善してよい。ただし公開 API・外部から観測可能な振る舞いは一切変えない。**

- **公開面は不可侵** — シグネチャ・公開型・公開モジュール構成・入出力・副作用・エラー条件・パニック条件を完全に保つ。既存テストは無修正で green になることが前提。テストが内部実装に依存していて壊れる場合は、そのテスト自体が実装詳細に踏み込みすぎている signal であり、brushup 側の設計不備ではない旨を提案時に指摘する
- **非公開実装は全面的な再設計の対象** — private な関数・構造体・モジュール内部構成・定義順序・アルゴリズムは、公開面を保つ範囲で自由に書き直してよい。より効率的なアルゴリズムへの差し替え、内部データ構造の変更も対象
- **磨く観点は明確に持つ** — 無駄な `clone()`/アロケーションの削減、重複コードの共通化、関数・構造体の定義位置とモジュール性、定義順序の意味づけ（呼び出し関係・抽象度・関心事によるグルーピング）、コードの汚さの解消
- **コードそのものが仕様書である** — 型・命名・構造で表現できることはそちらで表現し、ドキュメント・コメントは最後の手段にする

## 実行手順

このスキルは **2フェーズ** で進める。フェーズ1の提案が accept されるまで、ファイルへの書き込みは行わない。

### フェーズ1: brushup 設計の提案（accept 待ち）

1. **公開面の確定** — 対象コードを読み、`pub` なシグネチャ・型・モジュール構成、および入出力・副作用・エラー条件・パニック条件など外部から観測可能な振る舞いを洗い出し、「変えてはいけない境界」を明示する
2. **非公開実装の問題点の指摘** — 重複コード、無駄な alloc、モジュール構成の乱れ、定義順序に一貫性がない箇所など、磨くべき点を具体的に挙げる
3. **ブラッシュアップ後の内部設計の提示** — 公開面を変えずに実現する改善後の非公開実装を、関数分割・型設計・定義順序・モジュール構成で示す。一意に定まる部分は確定案として書く
4. **設計判断ポイントの抽出** — 合理的な選択肢が複数あり判断が分かれる箇所を番号付きで列挙し（詳細は「出力形式」）、各論点に方針 A/B/C とメリット・デメリット・推奨案を添える
5. **影響確認** — 公開面は変えない前提だが、`Grep` で実際の利用箇所を確認し、意図せず壊れる箇所がないことを裏付ける（あれば設計を見直す）

ここで提案を出し、**ユーザーの判断を待つ**。設計の方向性が固まるまでは実装に着手しない。

### フェーズ2: ブラッシュアップ実行（accept / 方針指定 後）

**入力形式（定型）**

| 入力 | 意味 |
|---|---|
| `accept` | 全設計判断ポイントで **推奨案** を採用する |
| `1=A,2=C` | 論点1は A、論点2は C を採用。**指定のない論点は推奨案** を採用する |
| `accept` + 補足文 | 推奨案ベースに、補足文の指示を上書きで反映する |
| 上記以外（設計そのものへの異論・追加要望・懸念） | フェーズ2には進まない。指摘・新設計にフィードバックを反映し、フェーズ1の提案をやり直す |

**実行手順**

6. **採用方針の確定** — 入力を上記の形式で解釈し、各論点で採用する方針を1行で復唱する（例: `論点1=A（推奨） / 論点2=C`）
7. **磨き直し** — 公開面は一切変えず、確定した設計で非公開実装のみを書き直す
8. **検証** — `cargo check` → `cargo clippy` → `cargo test` の順に実行して green にし、最後に `cargo fmt` を実行する。既存テストは無修正で通ることが前提であり、通らない場合は公開面に踏み込んでいないか設計を見直す

## ブラッシュアップの指針（Rust）

### 重複・アロケーション

- 重複コードは関数化でまとめる（ジェネリクス・マクロでの共通化は関数化で不十分な場合の最終手段）
- 無駄な `clone()`/`to_vec()`/`collect()` を削減し、イテレータチェーンで中間アロケーションを排除する。所有権を持つ必要がない箇所は参照で済ませ、必要に応じて `Cow` を活用する

### モジュール性・定義順序

- 公開/非公開の境界を見直し、関連する型・関数を近接配置する
- 定義順序は一貫した基準（呼び出し関係・抽象度・公開/非公開・関心事によるグルーピングなど）を持たせる
- 非公開ヘルパーは適切な粒度に分割・統合する（過度に細分化された関数はまとめ、肥大化した関数は責務ごとに分ける）

### イディオム・品質

- イテレータチェーン・`match`/`if let`/`let-else`/`matches!` の適切な使い分け、derive で済むトレイトの derive、マジックナンバー・マジック文字列の定数化

## コメント方針

コメントは書いた瞬間からコードと乖離するリスクを負う「負債」である。AI生成コードは過剰になりがちなので、磨き直しの段階で徹底的に絞る。

- **WHAT/HOW は書かず、WHY だけ残す** — コードを読めばわかることは削除し、変数名・関数名で表現しきれない非自明な理由（隠れた制約・仕様上の理由・不具合への回避策など）だけを、リポジトリ内の情報だけで理解できる形で残す
- **会話・一時情報・自明なイディオムへの言及は禁止** — ユーザーとのやり取りの引き写し、Issue番号など陳腐化する外部参照、`UnsafeCell` の `Send`/`Sync` 手動実装のような標準的イディオムへの説明は書かない
- **詳細仕様は doctest に逃がす** — 引数や挙動の詳細は `# Examples` の動作可能な doctest で示し、陳腐化を防ぐ
- **`// SAFETY:`** — `unsafe` で非自明な不変条件がある場合のみ要点を簡潔に書く（`transmute` の layout 保証なら `same layout` 程度で十分）
- **doc コメント（`///`/`//!`）は公開 API のみ** — `# Errors`/`# Panics`/`# Safety` は非自明な条件がある場合のみ設け、prose の箇条書きより doctest（`should_panic`、`Err` を返す例）での実演を優先する。他の型・関数への言及は `` [`Type`] `` で intra-doc link にする
- **英語のみでコメントする方針の場合は ASCII のみを使う** — em dash（—）や矢印（→ など）は使わない
- **文の区切りには `,` または `.` のみを使う** — `;` は意味が正しく伝わらないため使わない

**改行（rustfmt はコメントを再整形しないため厳守）**: 1文は改行せず1行で書き、画面幅に合わせた機械的な折り返しは禁止。改行してよいのは箇条書き項目間・見出し前後・コードブロック前後、または150文字超の文を読点等の切れ目でやむを得ず区切る場合のみ。段落途中に無駄な空行を挟まない

## 出力形式

### フェーズ1: 提案

```
## 公開面（変えないもの）
[pub なシグネチャ・型・モジュール構成、および外部から観測可能な入出力・副作用・エラー条件・パニック条件]

## 非公開実装の問題点
[重複コード、無駄な alloc、モジュール構成の乱れ、定義順序の一貫性のなさなど、磨くべき箇所]

## ブラッシュアップ後の内部設計
[公開面を変えずに実現する改善後の非公開実装。関数分割・型設計・定義順序・モジュール構成]
[判断が一意に定まる部分はここで確定案として記述する]

## 設計判断ポイント
判断が分かれる箇所のみを列挙する。`accept` で全て推奨案を採用、個別指定は `1=A,2=C` 形式。

### 1. [論点のタイトル]
- **A（推奨）**: [案] — 利点: [...] / 欠点: [...]
- **B**: [案] — 利点: [...] / 欠点: [...]
- **C**: [案] — 利点: [...] / 欠点: [...]
- 推奨理由: [なぜ A を推すか。1〜2行]

### 2. [論点のタイトル]
- **A（推奨）**: ...
- **B**: ...

## 影響確認（利用箇所）
- `ファイル名:行番号` — [公開面が保たれていることの確認結果]
```

**設計判断ポイントの作り方**

- **論点ごとに1番号、独立させる** — 番号間で互いに依存しないようにする
- **選択肢は A から順に、A は必ず推奨案** — 案が2つなら A/B、3つなら A/B/C
- **推奨は「最良の非公開実装」基準で選ぶ** — 変更量の少なさは理由にしない
- **利点・欠点は具体的に** — 「柔軟」「安全」のような抽象語で終わらせず、何がどう変わるかを書く
- **真に分かれるものだけ論点にする** — 推奨が明確で他案に意味がない場合は、新設計の確定案に含める

提案後、ユーザーの判断（`accept` または方針指定）を待つ。判断が来るまで実装しない。

### フェーズ2: ブラッシュアップ結果（accept / 方針指定 後）

- **採用方針**: 各論点で採用した方針の復唱（例: `論点1=A（推奨） / 論点2=C`）
- **磨いたもの**: 確定した設計での非公開実装のコード（公開面は無変更）
- **検証結果**: `cargo check` / `cargo clippy` / `cargo test`（既存テスト無修正で green） / `cargo fmt` の実行結果
- **要確認**: 自動検証で担保できない確認事項（実行時の挙動・パフォーマンス特性の変化など）。なければ「なし」
