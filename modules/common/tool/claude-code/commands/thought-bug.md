# バグ原因特定

**症状・起点**: $ARGUMENTS

> - **エラーメッセージ・症状指定**: それを起点に調査する
> - **ファイルパス指定**: そのファイルから調査を開始する
> - **未指定**: 直前の会話コンテキスト（エラーログ等）を起点にする

## 制約

- **コードの変更は行わない** — 修正方針の提示のみ。観察のためのコマンド実行（ログ確認・単体テスト記載・実行・`cargo check`/`cargo test`/`cargo run`・git 調査等）は行ってよい
- 推測と確認済みの事実を明確に区別する
- どの安価な観察でも確定できない仮説が残った場合は「特定できなかった理由」と「次の調査ステップ」を示す

## 調査プロセス

1. **症状の確認** — エラーメッセージ・再現手順・発生条件を整理する
2. **仮説の列挙** — 考えられる原因を最低3つ挙げる（決めつけない）
3. **反証観察の選定** — 各仮説について、それを反証できる最も安価な観察を1つ選ぶ（ログ1行・既存/最小の単体テスト・`cargo check`・hexdump・逆アセンブル等）
4. **安い順に実行** — 全仮説中で最も安価な観察から実際に実行し、結果を報告する。確定/反証できた仮説はそこで確定させ、残りの仮説について次に安価な観察を選び直して繰り返す
5. **根本原因の特定** — 直接原因だけでなく、なぜそれが起きたかまで掘り下げる
6. **修正方針の提案** — 修正案・影響範囲・テスト方針を提示する

## 調査観点

- 最近のコード変更（`git log --oneline`, `git diff`）
- 外部依存（ライブラリ・API・DB）のバージョンや変更
- 環境・設定の違い（dev/staging/prod）
- 競合状態（Race condition）やタイミング問題
- エッジケース・境界値・null/undefined の扱い
- 型の不一致やキャストのミス
