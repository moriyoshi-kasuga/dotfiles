# 仕様準拠実装（Rust）

**対象**: $ARGUMENTS

ファイルパスなら `Read` した内容、説明文ならそのテキストを仕様とする。未指定なら直前の会話で確定した仕様・修正計画（`/grill-me` 等での合意内容）を仕様とする。確定した仕様が存在しない場合は、その旨を伝えて `/grill-me` を先に使うよう促し、中断する。

## 原則

**「何を作るか」は所与、決めるのは「Rustとしてどう書くか」だけ。**

- 要件そのものへの疑義・改善提案・スコープ外の修正（ついでのリファクタ等）はしない
- 目的レベル（何を達成すべきか）が曖昧・矛盾・欠落している場合のみ `AskUserQuestion` で確認する
- 外部から見た振る舞いに影響しない技術選択（内部エラー型の形、関数分割、命名の細部など）は Rust として最も自然な形を自分で選ぶ。区別に迷ったら「振る舞いが変わるか」で判定する

## 実行手順

提案フェーズは持たない。`Edit`/`Write` は最初から使い、曖昧点の確認だけ実装着手前に済ませる。

0. `Skill(rust-coder)` を読み込む
1. 仕様を確定する。存在しない場合は中断してユーザーに伝える
2. 実装対象の入出力・振る舞い・エラー条件・制約を箇条書きで復唱し、認識のズレをこの時点で表面化させる
3. 目的レベルで曖昧・矛盾・欠落している箇所があれば `AskUserQuestion` で確認する。実装細部の技術選択はここで確認せず手順5で決める
4. 実装対象周辺の命名規約・モジュール構成・エラー型・依存関係を `Read`/`Grep` で把握し、仕様を実現する上でその流儀に合わせる
5. 仕様通りに実装する。仕様が規定していない技術選択は、決めた内容を出力形式に記録する
6. `rust-coder` の検証手順で green にする
7. 仕様の各項目が満たされているかを自己検証し、満たせなかった項目は「要確認」として明示する

`rust-coder` の設計方針・コメント方針に従うが、仕様が型・API・エラー表現を規定している場合はそちらを優先する。既存の関連コードとシグネチャ・振る舞いが矛盾する変更が必要になった場合、それ自体が仕様の曖昧点なので手順3に戻って確認する。実装中に気づいた既存コードの問題は直さず「要確認」に書く（対応は `/rewrite` `/brushup` `/refine` の領分）。

## 出力形式

```
## 確定した仕様
[復唱した入出力・振る舞い・エラー条件・制約]

## 実装したもの

## 実装時に決めた技術選択
[仕様が規定していなかったため自分で判断した技術選択とその理由。なければ「なし」]

## 検証結果

## 仕様との対応
- [仕様項目] — 満たした/満たしていない

## 要確認
[自動検証で担保できない確認事項、仕様と既存コードが矛盾していた箇所など。なければ「なし」]
```
