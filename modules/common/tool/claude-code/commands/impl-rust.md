# 仕様準拠実装（Rust）

**対象**: $ARGUMENTS

> - **ファイルパス指定あり**: `Read` して仕様書とする
> - **説明文の指定あり（ファイルでない）**: そのテキストを仕様とする
> - **未指定**: 直前の会話で確定した仕様・修正計画（`/grill-me` `/planning` 等での合意内容）を仕様とする。会話中に確定した仕様が存在しない場合は、その旨を伝えて `/grill-me` または `/planning` を先に使うよう促し、中断する

## 哲学

**「何を作るか」は既に決まっている。このスキルが決めるのは「Rustとしてどう書くか」だけ。**

- **仕様は所与とする** — `/rewrite` `/brushup` `/refine` のように対象コードから設計を導出しない。入力された仕様・修正計画をそのまま実装対象とし、要件そのものへの疑義・改善提案はここでは行わない
- **目的レベルの曖昧さは質問する、実装細部は自分で決める** — 仕様が「何を達成すべきか」で曖昧・矛盾・欠落している場合は、憶測で埋めずに `AskUserQuestion` で確認する。一方、仕様が明示していない実装上の技術選択（内部エラー型の形、関数分割、命名の細部など、外から見た振る舞いに影響しない部分）は、Rustとして最も自然な形を自分で選んで実装する。区別に迷ったら「振る舞いが変わるか」で判定する
- **スコープを超えない** — 仕様にない改善・リファクタ・ついでの修正はしない。実装の過程で気づいた既存コードの問題は、直さず「要確認」として報告するに留める（対応は `/rewrite` `/brushup` `/refine` 等の領分）
- **コードそのものが仕様書である** — 型・命名・構造で表現できることはそちらで表現し、ドキュメント・コメントは最後の手段にする

## 実行手順

このスキルは提案フェーズを持たない。仕様は既に確定しているため `Edit`/`Write` は最初から使う。曖昧点の確認だけは実装着手前に済ませる。

1. **仕様の確定** — 上記の入力ルールに従い仕様・修正計画を確定する。仕様が存在しない場合は中断してユーザーに伝える
2. **仕様の復唱** — 実装対象の入出力・振る舞い・エラー条件・制約を箇条書きで復唱する。ユーザーとの認識のズレをこの時点で表面化させる
3. **曖昧点の確認** — 仕様が目的レベルで曖昧・矛盾・欠落している箇所を洗い出し、あれば `AskUserQuestion` で確認する。実装細部の技術選択はここで確認せず自分で決める（5で明示する）
4. **既存コードとの整合確認** — 実装対象周辺の既存コード（命名規約・モジュール構成・エラー型・依存関係）を `Read`/`Grep` で把握し、仕様を実現する上でその流儀に合わせる
5. **実装** — 確定した仕様通りに実装する。仕様が規定していない技術選択は、この場で決めた内容を出力形式の「実装時に決めた技術選択」に記録する
6. **検証** — `cargo check` → `cargo clippy` → `cargo test` の順に実行して green にし、最後に `cargo fmt` を実行する
7. **仕様との対応確認** — 仕様の各項目が実装で満たされているかをチェックリストで自己検証する。満たしていない・満たせなかった項目があれば「要確認」として明示する

## 実装の指針（Rust）

仕様が明示していない範囲でのみ以下を判断基準にする。仕様が既に型・API・エラー表現を規定している場合はそちらを優先する。

### 型・API設計

- 実行時チェックで守るくらいなら型（newtype・enum・ジェネリクス境界）で不正な状態を表現不可能にする
- `pub` の範囲は仕様が要求する最小限に留める。仕様にない公開APIを追加しない
- 不要な `clone()`/アロケーションを避け、イテレータ・ゼロコスト抽象を使う。リソース管理は RAII（`Drop`）に任せる

### 既存コードとの整合

- 命名規約・モジュール構成・エラー型（`thiserror`/`anyhow` の使い分けなど）は、仕様が指定しない限り既存コードの流儀に合わせる。前例がない新規箇所でのみ自分の判断で決める
- 既存の関連コードとシグネチャ・振る舞いが矛盾する変更が必要になった場合、それ自体が仕様の曖昧点なのでステップ3に戻って確認する

### イディオム・品質

- イテレータチェーン・`match`/`if let`/`let-else`/`matches!` の適切な使い分け、derive で済むトレイトの derive、マジックナンバー・マジック文字列の定数化

## コメント方針

コメントは書いた瞬間からコードと乖離するリスクを負う「負債」である。AI生成コードは過剰になりがちなので徹底的に絞る。

- **WHAT/HOW は書かず、WHY だけ残す** — コードを読めばわかることは削除し、変数名・関数名で表現しきれない非自明な理由（隠れた制約・仕様上の理由・不具合への回避策など）だけを、リポジトリ内の情報だけで理解できる形で残す
- **会話・一時情報・自明なイディオムへの言及は禁止** — ユーザーとのやり取りの引き写し、Issue番号など陳腐化する外部参照、`UnsafeCell` の `Send`/`Sync` 手動実装のような標準的イディオムへの説明は書かない
- **詳細仕様は doctest に逃がす** — 引数や挙動の詳細は `# Examples` の動作可能な doctest で示し、陳腐化を防ぐ
- **`// SAFETY:`** — `unsafe` で非自明な不変条件がある場合のみ要点を簡潔に書く（`transmute` の layout 保証なら `same layout` 程度で十分）
- **doc コメント（`///`/`//!`）は公開 API のみ** — `# Errors`/`# Panics`/`# Safety` は非自明な条件がある場合のみ設け、prose の箇条書きより doctest（`should_panic`、`Err` を返す例）での実演を優先する。他の型・関数への言及は `` [`Type`] `` で intra-doc link にする
- **英語のみでコメントする方針の場合は ASCII のみを使う** — em dash（—）や矢印（→ など）は使わない
- **文の区切りには `,` または `.` のみを使う** — `;` は意味が正しく伝わらないため使わない

**改行（rustfmt はコメントを再整形しないため厳守）**: 1文は改行せず1行で書き、画面幅に合わせた機械的な折り返しは禁止。改行してよいのは箇条書き項目間・見出し前後・コードブロック前後、または150文字超の文を読点等の切れ目でやむを得ず区切る場合のみ。段落途中に無駄な空行を挟まない
