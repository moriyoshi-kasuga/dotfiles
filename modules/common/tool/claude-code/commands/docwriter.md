# ドキュメント最小再構築（Rust特化）

**対象範囲**: $ARGUMENTS（未指定なら `git diff HEAD` の変更範囲）

## 前提

既存のコメントはコードの変更に追従していないことが多いため、内容を一切当てにしない。現在のコードの型・シグネチャ・制御フローだけを根拠に、必要な部分をゼロから書き直す。
ドキュメントは書くほど保守コストになるため、量より正確さを優先し、原則として最小限に留める。

## 書かないもの

- 既存の文章の要約・編集による引き継ぎ。一度すべて削除してから書き直す
- それ以外は `rust-coder` スキル（手順0で読み込み済み）の「書かないもの」に従う（WHAT/HOW、会話由来の思想、旧APIとの差分、呼び出し元・利用箇所の説明、太字/体言止め＋コロンの強調表現など）

## 書くもの

- 使い方や挙動は、長文の説明ではなく `# Examples` の doctest で表現する
- 公開 API・非公開の項目ともに、必要最低限の記述にとどめる
- どうしても文章が必要な場合も、既存の文章は読まず、コードから読み取れる最重要点のみを1〜2文程度で書く
- その他の書き方（`// SAFETY:` の要件、改行・句読点のルールなど）は `rust-coder` スキルに従う

対象は行コメント（`//`）・ブロックコメント（`/* */`）・doc コメント（`///` `//!`）・`// SAFETY:` と doctest のみ。コードそのものは変更しない。

## 実行手順

0. `Skill(rust-coder)` を読み込み、共通のコメント方針を確認する
1. 対象を確定し、その範囲の既存コメントを一度すべて削除する
2. コメントを削除したコード（型・シグネチャ・制御フロー）だけを見て、必要な doc コメント・SAFETY コメント・doctest をゼロから設計する。既存の文章・会話の履歴は参照しない
3. 会話由来の思想・旧APIとの差分・呼び出し元の説明・太字や「：」の強調・不自然な改行が混入していないか見直す。コード上の挙動と説明が一致しない箇所（不具合の疑い）を見つけた場合、それを正しい挙動として文書化せず「要確認」に挙げ、`/thought-bug` での原因特定を提案する
4. `cargo test --doc` を実行し、doctest が通ることを確認する

## 出力形式

**削除した不要コメント**（ファイルと箇所、どういうコメントか） / **追加・改善した doctest**（doctest で表現した仕様） / **残した最小限のコメント**（残す必要があった WHY・SAFETY） / **検証結果**（`cargo test --doc` の結果と、不自然な改行がないか） / **要確認**（コードと既存コメントの記述が食い違い不具合が疑われる箇所。なければ「なし」）
