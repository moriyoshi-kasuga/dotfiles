# ドキュメント最小再構築（Rust特化）

**対象範囲**: $ARGUMENTS

## 前提

既存のコメント・ドキュメントはコードの変更に追従していないことが多く、当てにしない。
そのため既存の文章は参考にせず、現在のコードの型・シグネチャ・制御フローのみを根拠に、必要な部分だけをゼロから書き直します。
ドキュメントは書くほど保守コストになるため、量より正確さを優先し、原則として最小限に留めます。

## 方針

- 既存のコメントは一度すべてクリアしてから書き直す。既存の文章を要約・編集して引き継ぐことはしない。
- コードを読めば分かることは書かない。変数名・型・関数分割で表現できるなら、コメントは不要。
- 言語仕様や標準ライブラリの挙動、`Send`/`Sync` の一般的なイディオムなど、自明な内容の説明は書かない。
- ユーザーとの会話で伝えた設計意図・思想はそのまま転記しない。会話は陳腐化前提の一時的な文脈であり、リポジトリ内の情報だけで理解できる記述に変換する。
- 「以前は〜だった」「〜から変更された」のような旧APIとの差分・変更履歴は書かない。変更履歴は git log・git diff が担当する領域であり、ドキュメントは現在のコードの状態のみを説明する。
- 「このクレートの〜で使われる」「ここでは〜のために呼ばれる」のような呼び出し元・利用箇所の説明は書かない。利用状況は変更されやすく陳腐化するため、対象自体の入力・出力・不変条件のみを書く。
- 使い方や挙動を示したい場合は、長文の説明ではなく `# Examples` の doctest で表現する。
- 公開 API・非公開の項目ともに、必要最低限の記述にとどめる。公開 API には doc コメント（`///`）を付け、非公開の項目には非自明な WHY がある場合のみ `//` で一文程度のコメントを残す。
- `// SAFETY:` コメントは、呼び出し側・実装側が満たすべき非自明な前提条件がある場合のみ書く。
- 太字（`**`）や体言止め＋「：」を多用する箇条書き的な強調表現は使わない。読点・句点を使った通常の文章として書く。doc コメントは Markdown としてレンダリングされるため、プレーンな説明文の方が過剰な装飾より自然に読める。
- 文の区切りには `,` または `.` のみを使い、`;` は使わない。`;` は意味が正しく伝わらない。
- どうしても文章が必要な場合も、既存の文章は読まず、コードから読み取れる最重要点のみを1〜2文程度で書く。
- コードそのものは変更しない。対象はコメントと doctest のみ。

## 対象

- 行コメント（`//`）・ブロックコメント（`/* */`）
- doc コメント（`///` / `//!`）
- `unsafe` ブロックの `// SAFETY:` コメント

## 改行・整形規則

- 改行してよいのは、箇条書きの項目間、セクション見出しの前後、コードブロックの前後、および1文が150文字を超え途中で区切る必要がある場合のみ。
- 段落の途中に無駄な空行を挟まない。

## 実行手順

1. `$ARGUMENTS` から対象ファイル・箇所を確定する。未指定なら `git diff HEAD` の変更範囲を対象にする。
2. 対象範囲の既存コメント（`//`, `/* */`, `///`, `//!`）を一度すべて削除する。
3. コメントを削除したコード（型・シグネチャ・制御フロー）だけを見て、必要な doc コメント・SAFETY コメント・doctest をゼロから設計する。既存の文章・会話の履歴は参照しない。
4. 改行・整形規則に沿って文章を整える。会話由来の思想・旧APIとの差分・呼び出し元の説明・太字や「：」を多用した強調表現が混入していないか見直す。
5. `cargo test --doc` を実行し、doctest が通ることを確認する。
6. 変更内容を報告する。

## 出力形式

### 変更内容のサマリー

- **削除した不要コメント**: どのファイルのどの箇所にあった、どういうコメントを削除したか
- **追加/改善した doctest**: ドキュメントの代わりに doctest で表現した仕様の要約
- **残した最小限のコメント/docコメント**: 残す必要があった WHY や SAFETY の説明

### 検証結果

`cargo test --doc` の実行結果と、不自然な改行がないか確認した旨を報告する。
