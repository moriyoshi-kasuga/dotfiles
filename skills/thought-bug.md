# バグ原因特定

**症状・起点**: $ARGUMENTS（未指定なら直前の会話のエラーログ等）

コードの変更は行わない（観察のためのコマンド実行はよい）。推測と確認済みの事実を明確に区別する。

症状を整理し、考えられる原因を最低3つ挙げる。各仮説について、それを反証できる最も安価な観察（ログ1行・既存/最小の単体テスト・`cargo check`・hexdump等）を選び、全仮説中で最も安価なものから実際に実行する。確定/反証した仮説はそこで確定させ、残りは次に安価な観察で繰り返す。直接原因だけでなくなぜそれが起きたかまで掘り下げ、修正案・影響範囲・テスト方針を示す。どの観察でも特定できなければ、理由と次の調査ステップ（より高コストな観察も含め）を示す。

根本原因が特定できたら、修正の性質に応じて次のスキルを1つ提案する: 入出力・振る舞いが確定していて実装だけが要る → `/impl-rust`。公開API・振る舞いは変えず内部実装だけの欠陥 → `/brushup`。公開APIの使い勝手自体が原因 → `/refine`。設計そのものが根本的に破綻 → `/rewrite`。

## 出力

症状 / 仮説と反証観察 / 安い順の調査ログ（観察→結果→判定）/ 根本原因（or 特定できない理由と次のステップ）/ 修正方針 / 影響範囲 / 次のステップ。
