# バグ原因特定

**症状・起点**: $ARGUMENTS（未指定なら直前の会話のエラーログ等）

コードの変更は行わない（観察のためのコマンド実行はよい）。推測と確認済みの事実を明確に区別する。

症状を整理し、考えられる原因を最低3つ挙げる。各仮説について、それを反証できる最も安価な観察（ログ1行・既存/最小の単体テスト・`cargo check`・hexdump等）を選び、全仮説中で最も安価なものから実際に実行する。1つの観察で複数の仮説を同時に判定できる場合はそれを優先する。確定/反証した仮説はそこで確定させ、残りは次に安価な観察で繰り返す。

観察は「無料〜安価」（`Read`/`Glob`/`Grep`・git系コマンド・`cargo check`・フィルタで絞った単体テスト1本）と「高価」（フィルタなしの`cargo test`・`cargo run`・実行時間が見積もれない観察）の2段階に分ける。無料〜安価な観察が残っている限りは上限なく安い順に実行してよいが、高価な観察しか残っていない状態になったら、症状（`$ARGUMENTS`）にその具体的な再現手順が明示されている場合を除き、そこで一旦止める。ここまでの調査結果と次に実行したい高価な観察・理由を提示し、ユーザーの指示を待ってから実行する。

直接原因が1つに絞れても止めず、「なぜそれが起きたか」をさらに掘り下げる（例: nullチェック漏れ → なぜ漏れたか → 型設計上そのケースを表現できていない、など）。表面的な原因と構造的な原因を区別し、後者まで到達できるよう追加の観察を続ける。どの観察でも特定できなければ、理由と次の調査ステップ（より高コストな観察・再現手順の追加取得なども含め）を示す。

## 出力

症状 / 仮説と反証観察 / 安い順の調査ログ（観察→結果→判定）/ 直接原因と構造的原因（or 特定できない理由と次のステップ）/ 影響範囲（同じ構造的原因が波及しうる箇所）/ 次の調査ステップ。
