# ブラッシュアップ

**対象**: $ARGUMENTS

## 進め方

**対象の決め方** — パス・箇所の指定があればそれを対象にする（説明文なら `Glob`/`Grep` で特定し、提案の冒頭で対象を明示する）。未指定なら直前の作業対象または `git diff HEAD`。差分が無関係な複数の変更にまたがる場合は範囲を先に確認する。

**フェーズ運用** — フェーズ1ではファイルへの書き込みを一切せず設計を提案し、ユーザーの判断を待つ。`accept` は全論点で推奨案を採用、`1=A,2=C` は指定論点のみ差し替えて残りは推奨案、`accept` + 補足文は推奨案ベースに補足を上書きする。それ以外（設計への異論・追加要望・懸念）はフェーズ2に進まず、フィードバックを反映してフェーズ1をやり直す。フェーズ2の冒頭では採用方針を1行で復唱する。

## 哲学

**refactor は処理を完全に保ったままコードの見た目だけを変える。brushup は非公開実装であれば処理内容そのものを改善してよい。公開API・外部から観測可能な振る舞いは、変える価値がないかぎり変えない。**

- **公開面は原則不可侵** — シグネチャ・公開型・公開モジュール構成・入出力・副作用・エラー条件・パニックや例外の条件は基本的に保つ。既存テストは無修正で green になることが前提
- **ただし「一切変えない」は目的ではない** — 実装を磨く過程で、観測可能な振る舞い自体がその場しのぎ・バグ・一貫性のない仕様になっている箇所に気づくことがある。修正する価値があると判断したら、隠さず設計判断ポイントとして提案する。黙って直さない（brushup の契約を超える変更を確定案に紛れ込ませない）し、黙って見逃さない（気づいた不備を報告しないのも不誠実）
- **振る舞いを変える案を採用した場合のみ、関係するテストを修正してよい** — 対象は「その振る舞いを検証しているテスト」に限る。ついでに他のテストへ手を広げない。テストが内部実装の詳細（非公開関数の呼び出し回数・内部データ構造など）に依存していて壊れる場合は、そのテスト自体が実装詳細に踏み込みすぎている signal であり、brushup 側の設計不備ではない旨を提案時に指摘する
- **非公開実装は全面的な再設計の対象** — private な関数・型・モジュール内部構成・定義順序・アルゴリズムは、公開面を保つ範囲で自由に書き直してよい。より効率的なアルゴリズムへの差し替え、内部データ構造の変更も対象

## 非公開実装の観点

- **DRY（Don't Repeat Yourself）** — 重複コードを関数化でまとめる。3箇所以上に広がる同一ロジックは特に優先する。関数化で共通化しきれない場合のみジェネリクス・高階関数など次の手段を検討する
- **KISS（Keep It Simple）** — 不要な間接化・抽象化・分岐を削る。同じ結果を素直に書ける箇所を凝った書き方にしない。無駄な中間データ構造・コピー・計算を削減し、必要な分だけ処理する
- **YAGNI（You Aren't Gonna Need It）** — 使われていない汎用化・将来のための拡張ポイント・呼ばれない分岐を削る。「いつか要るかもしれない」を残す理由にしない
- **凝集度と粒度** — 関連する型・関数を近接配置し、定義順序は一貫した基準（呼び出し関係・抽象度・関心事によるグルーピングなど）を持たせる。非公開ヘルパーは適切な粒度に分割・統合する（過度に細分化された関数はまとめ、肥大化した関数は責務ごとに分ける）
- **公開/非公開境界の見直し** — 非公開で足りるのに公開されている、逆に非公開実装が肥大化して公開すべき単位が埋もれている、といった境界の乱れを整理する
- **コメントの鮮度** — 既存コメントが非公開実装の変更に追従できているかを磨き直しの段階で見直す

## 実行手順

### フェーズ1: brushup 設計の提案

1. **公開面の確定** — 対象コードを読み、公開シグネチャ・型・モジュール構成、および入出力・副作用・エラー条件・パニックや例外の条件など外部から観測可能な振る舞いを洗い出し、「変えてはいけない境界」を明示する
2. **非公開実装の問題点** — 「非公開実装の観点」に基づき、磨くべき点を具体的に挙げる
3. **ブラッシュアップ後の内部設計** — 公開面を変えずに実現する改善後の非公開実装を、関数分割・型設計・定義順序・モジュール構成で示す。一意に定まる部分は確定案として書く
4. **観測可能な振る舞いに関する修正提案（該当する場合のみ）** — 1〜3の過程で気づいた、実装として不適切な観測可能な振る舞い（バグ・一貫性のなさ・意図が読めない仕様）があれば、確定案には含めず設計判断ポイントに起こす。関係するテストの修正要否も明記する
5. **設計判断ポイント** — 判断が分かれる箇所を、下記の書式で列挙する。4の提案は確信度に関わらず必ずここに含める
6. **影響確認** — 公開面を変えない前提の箇所について、`Grep` で実際の利用箇所を確認し、意図せず壊れる箇所がないことを裏付ける（あれば設計を見直す）

### フェーズ2: ブラッシュアップ実行

7. 採用方針を復唱し、確定した設計で非公開実装を書き直す。振る舞いを変える案を採用した場合はそれも反映し、影響する呼び出し元があれば追従する
8. 対象言語・プロジェクトの既存のビルド/lint/テストコマンドで green にする。振る舞いを変えていない範囲は既存テスト無修正で通ることが前提であり、通らない場合は公開面に踏み込んでいないか設計を見直す。振る舞いを変える案を採用した場合は、その振る舞いを検証するテストのみ意図を保って書き直す

## 設計判断ポイントの書式

合理的な選択肢が複数あり判断が分かれる箇所だけを、次の書式で列挙する。

```
### 1. [論点のタイトル]
- **A（推奨）**: [案] — 利点: [...] / 欠点: [...]
- **B**: [案] — 利点: [...] / 欠点: [...]
- 推奨理由: [なぜ A を推すか。1〜2行]
```

論点ごとに1番号を振り、番号間で互いに依存しないよう独立させる。選択肢は A から順に並べ、A を必ず推奨案にする。利点・欠点は「柔軟」「安全」のような抽象語で終わらせず、何がどう変わるかを書く。推奨が明確で他案に意味がないものは論点にせず新設計の確定案に含める。ただし観測可能な振る舞いを変える提案だけは、推奨が明確でも必ず論点として明示する（brushup の契約を超える変更をユーザーの判断なしに確定案へ混ぜない）。

## 出力形式

### フェーズ1: 提案

```
## 公開面（変えないもの）
[公開シグネチャ・型・モジュール構成、および外部から観測可能な入出力・副作用・エラー条件・パニックや例外の条件]

## 非公開実装の問題点
- `ファイル名:行番号` — [問題の説明]（原則: DRY/KISS/YAGNI/凝集度/公開境界/コメント鮮度）

## ブラッシュアップ後の内部設計
## 設計判断ポイント
## 影響確認（利用箇所）
- `ファイル名:行番号` — [公開面が保たれていることの確認結果]
```

推奨は「最良の非公開実装」基準で選ぶ。観測可能な振る舞いを変える論点だけは、呼び出し側・利用者にとっての妥当性を基準にする。

### フェーズ2: ブラッシュアップ結果

**採用方針** / **磨いたもの**（非公開実装の変更点） / **振る舞いの変更**（採用した場合のみ、変更内容と追従したテスト。なければ「なし」） / **検証結果** / **要確認**（自動検証で担保できない確認事項。実行時の挙動・パフォーマンス特性の変化など。なければ「なし」）
</content>
