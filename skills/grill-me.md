# 計画のグリル

**テーマ**: $ARGUMENTS

## 原則

- **調査を質問より優先する** — コードベース・既存の計画・関連ファイルを調査すれば答えが出る論点は、質問せず調査する
- **質問すべき論点の見極めに比重を置く** — 洗い出した論点のうち、こちらで正当に推測できるものは推測して仮定として進め、ユーザーの意図を正当に推測できない論点だけを質問として残す
- **推奨案を必ず添える** — 質問にも仮定にも、推奨する内容とその理由を添える。選択肢を並べて判断を丸投げしない
- **互いに疎な論点はまとめて質問する** — 一方の回答が他方の前提・選択肢を変えない論点は、同じラウンドでまとめて質問する
- **依存関係のある論点は順番に解決する** — 一方の回答次第で他方の前提や選択肢自体が変わる論点は、同じラウンドにまとめない。依存元だけを先に質問し、回答を得て前提を更新した上で、次のラウンドで依存先を質問する
- **AskUserQuestionは1ラウンド最大4問** — ツールの制約であり、質問はこの範囲に収める。それでも論点が多い場合は、影響の小さいものを質問せず仮定に回す
- **大きく分岐する論点を先に質問する** — 後続の調査・設計・他の論点の前提を左右するもの（アーキテクチャ選択、責務分割など）から解決する。細部の論点は後回しにするか、質問せず仮定する
- **ラウンド数は最小に抑える** — 依存関係により複数ラウンドが必要な場合でも、原則1〜2ラウンドで共通認識に到達することを目指す。ラウンドを重ねるたびに「本当に質問が必要か」を問い直す

## 手順

1. **調査** — テーマ・対象パスに関わるコードベース・既存の計画を調査し、論点を洗い出す。現状・制約・依存関係を `ファイル名:行番号` で確認する。
2. **最大の対立点を特定する** — 調査結果とユーザーの計画・要望の間にある、最も大きい設計上の対立・矛盾を一つ選ぶ。なければ「対立点なし」と明示する。
3. **論点を分類する** — 洗い出した論点それぞれを次のいずれかに振り分ける。
   - 調査で答えが出た、または正当な推測ができる → 質問せず仮定として明示する
   - ユーザーの意図を正当に推測できない → 質問対象にする
4. **質問対象を絞り込む** — 質問対象のうち、他の判断への影響が大きい（分岐が広い）ものを優先し、最大4問に絞る。溢れた分は仮定に回す。
5. **依存関係を確認する** — 質問対象同士に依存がある場合、依存先を今回のラウンドから外し、依存元の回答を得てから次のラウンドで質問する。互いに疎なものは同じラウンドにまとめる。
6. **1メッセージで提示する** — 下記の出力形式で1メッセージにまとめて出し、ユーザーの回答を待つ。

## 出力形式

1メッセージに以下をこの順で含める。

### (a) 最大の設計上の対立
発見した最も大きい対立・矛盾を `ファイル名:行番号` の根拠とともに示す。対立点がなければその旨を述べる。

### (b) 推奨する解決方針
(a) に対して推奨する解決策と理由。

### (c) 質問
AskUserQuestionで、意図を正当に推測できない論点のみを最大4問まとめて質問する。互いに疎な論点を優先してまとめ、最も分岐が大きいものを先に置く。各質問には推奨する回答を用意する。質問すべき論点がなければこの節は省略する。

### 仮定
(c) 以外の論点をすべてここに明示する。何を仮定したか、なぜその仮定が妥当と考えたかを一言添える。

## 続き

回答を受けて調査・仮定を更新し、依存関係にあった論点が新たに質問可能になった場合は、同じ出力形式で次のラウンドを提示する。全論点について共通認識（または仮定の承認）に達したら、議論した論点と結論を簡潔に列挙して締める。
