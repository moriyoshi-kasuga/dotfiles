# Rust実装の共通方針

**対象**: $ARGUMENTS

他のRustスキル（`/impl-rust` `/rewrite` `/refine` `/docwriter` `/thought-bug` `/grill-me`）から共通方針として読み込まれる。各スキル固有の指示と矛盾する場合はスキル側を優先する。引数付きで直接実行した場合は下記「単体実行」の通り自分で判断してその場で実装する。引数なしならこの方針をそのまま表示する。

## 設計方針

不正な状態は実行時チェックより型（newtype・enum・境界）で表現不可能にする。`pub` は必要最小限にし、無駄なアロケーション・コピーは避け、リソース管理はRAIIに任せる。命名・モジュール構成・エラー型の流儀は既存コードに合わせ、前例がなければ自分で判断する。`#[non_exhaustive]` や `#[must_use]` のような属性は、その効果が実際に要る場合だけ付ける。

## コメント方針

コメントは書いた瞬間からコードと乖離する負債であり、AI生成コードは過剰になりがちなので徹底的に絞る。名前・型・構造で表現できることは書かず、名前で表現しきれない非自明なWHY（隠れた制約・仕様上の理由・不具合の回避策）だけを残す。変更履歴・会話の引き写し・呼び出し元への言及・陳腐化する外部参照は書かない。アイテムには `///`/`//!`、内部ロジックの補足だけ `//` にする。挙動の実演は文章より `# Examples` の doctest に逃がし、`// SAFETY:` は非自明な不変条件がある場合のみ書く。太字や体言止め＋コロンを並べる強調表現ではなく、通常の文章で書く。

## 検証手順

`cargo check` → `cargo clippy` → `cargo test` → 最後に `cargo fmt`。

## 提案フェーズの共通ルール

`/rewrite` `/refine` はまず提案し、ユーザーの合意を得てから書き込む。対象はパス指定があればそれ、未指定なら直前の作業対象か `git diff HEAD`。判断が割れる論点は選択肢とその推奨・理由を添えて提示し、それ以外の合理的な唯一解は確定案に含めてよい。ユーザーの反応が承認なら実行、異論・追加要望ならフィードバックを踏まえて提案をやり直す。

## スキル連携

- 小さくてさくっと済ませたい → `/rust-coder` を引数付きで直接実行
- 要件・仕様が固まっていない → `/grill-me`（決定事項を `/impl-rust` に渡せる形でまとめる）
- 確定した仕様に忠実に実装 → `/impl-rust`
- 公開APIを変えず非公開実装だけ磨く（汎用） → `/brushup`
- 責務・不変条件は保ったまま公開APIの使い勝手を改善 → `/refine`
- ゼロベースで設計し直す → `/rewrite`
- 既存コメントを当てにせず最小限のドキュメントに書き直す → `/docwriter`
- バグの原因が特定できていない → `/thought-bug`

対象範囲と無関係な既存の不具合に気づいたら、その場で直さず `/thought-bug` を提案する。

## 単体実行（$ARGUMENTS 指定時）

提案フェーズを設けず直接実装する。対象を決め、周辺の流儀を把握し、目的レベルで曖昧な点だけ `AskUserQuestion` で確認し、上記方針に従って直接変更し、検証手順でgreenにする。複数の妥当な設計が競合する規模だと気づいたら、その場で進めず適切なスキル（`/brushup` `/refine` `/rewrite` `/impl-rust`）を提案して止める。

変更内容・検証結果・要確認事項を簡潔に報告する。
