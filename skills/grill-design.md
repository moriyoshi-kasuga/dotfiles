# 設計思想のグリル

**テーマ**: $ARGUMENTS

> - **対象パス・モジュール名の指定**: そのコードにある設計判断を洗い出して議論する
> - **設計判断そのものの指定**: それを起点に深掘りする
> - **未指定**: 直前の会話コンテキスト、または直近の差分から議論対象を推測する

本スキルは `/grill-me` を土台とする。次の原則は `/grill-me` と共通のため重複定義せず、そのまま適用する。

- 調査を質問より優先する（コードベースを調査すれば答えが出る問いは質問しない）
- 推奨案を必ず添える（選択肢を並べて判断を丸投げしない）

## 原則（grill-design固有）

- **実装・コード変更は行わない** — 議論と論点整理のみ
- **意図はユーザーに聞く、コードから逆算しない** — 対象の設計意図は必ずユーザー自身の説明を起点にする。「なぜこうなっているか」をコードから先に推測して提示することはしない
- **事実と推測を区別する** — コードの現状は `ファイル名:行番号` で根拠を示し、意図とのギャップの評価・提案とは分けて書く
- **一論点ずつ提示する** — 対象に複数の設計判断が含まれる場合も、まとめて出さず一つずつユーザーと合意してから次に進む
- **対抗案は現状設計の制約に縛られない** — 現状のコード構造・依存関係への追従を前提とせず、ユーザーの意図を最も実現する設計を優先して提案する

## 手順

1. **設計意図の確認** — 対象について、ユーザーが望む設計意図・要望を確認する。$ARGUMENTS や会話にすでに説明されていればそれを採用する。明示されていなければ、コードから推測せずAskUserQuestionで直接尋ねる。
2. **現状コードの調査** — 1で得た意図に照らして対象コードの設計を調査する。Read/Glob/Grepで該当コードを確認し、必要なら `git log`/`git show`/`git blame` で導入時期・経緯を追う。
3. **論点への分解** — 意図と現状コードの間にあるギャップ・制約・トレードオフを一論点ずつ洗い出す。
4. **論点ごとに以下を組み立てる**（出力形式に従う）。
5. **一論点ずつ提示し、ユーザーと議論する**。ユーザーの反論・追加情報・意図の修正を受けたら、その場で調査し直して評価を更新する。合意（または「保留」の判断）に達したら次の論点に進む。
6. 議論の結果、設計変更が望ましいという結論になった場合でも、この場では実装しない。変更に進みたい場合は `/grill-rust` や `/impl-rust` など実装系スキルへの引き継ぎを提案する。

## 論点ごとの出力形式

### 論点: [対象の設計判断]

**ユーザーの意図**: ユーザーが説明した設計意図・要望（要約。ニュアンスを保つ）

**現状の設計**: 該当コードの説明。根拠は `ファイル名:行番号`

**意図とのギャップ**: 現状の設計が意図をどこまで満たしているか／満たしていないか。コード上の制約がある場合はその根拠

**現状設計の制約・理由の推測**: なぜ現状こうなっているか。コード・履歴に根拠があれば引用し、なければ「根拠が見当たらず推測」と明示する

**対抗案**（現状設計の制約に縛られない）:

#### 案A: [名前]

- 意図の実現度: ...
- メリット: ...
- デメリット: ...

#### 案B: [名前]

- 意図の実現度: ...
- メリット: ...
- デメリット: ...

（他に妥当な案があれば追加する）

**推奨**: ユーザーの意図を最も実現する案とその理由。現状維持が最善と判断した場合はその理由を明記する

## 完了報告

全論点についてユーザーと合意（または保留の判断）に達したら、議論した論点と結論を簡潔に列挙して締める。ファイルへの保存は行わない（必要であればユーザーから明示的に依頼された場合のみ行う）。
