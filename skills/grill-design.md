# 設計思想のグリル

**テーマ**: $ARGUMENTS

> - **対象パス・モジュール名の指定**: そのコードにある設計判断を洗い出して議論する
> - **設計判断そのものの指定**: それを起点に深掘りする
> - **未指定**: 直前の会話コンテキスト、または直近の差分から議論対象を推測する

## 原則

- **実装・コード変更は行わない** — 議論と論点整理のみ
- **事実と推測を区別する** — コードの現状は `ファイル名:行番号` で根拠を示し、意図の推測・評価とは分けて書く
- **一論点ずつ提示する** — 対象に複数の設計判断が含まれる場合も、まとめて出さず一つずつユーザーと合意してから次に進む
- **決めつけない** — 「なぜこうなっていないのか」という疑問は、コードベース・コミット履歴から根拠を探した上でなお不明な場合のみ推測と明示して提示する
- コードベースを調査すれば答えが得られる問いは、ユーザーに聞かず調査する

## 手順

1. **対象の特定** — テーマ・対象パスから、議論すべき設計判断を洗い出す。一つの対象に複数の判断が含まれる場合は論点に分解する。
2. **論点ごとの調査** — Read/Glob/Grepで該当コードを確認し、必要なら `git log`/`git show`/`git blame` で導入時期・経緯（コミットメッセージ、関連するリファクタ）を追う。
3. **論点ごとに以下を組み立てる**（出力形式に従う）。
4. **一論点ずつ提示し、ユーザーと議論する**。ユーザーの反論・追加情報・別の意図の指摘を受けたら、その場で調査し直して評価を更新する。合意（または「保留」の判断）に達したら次の論点に進む。
5. 議論の結果、設計変更が望ましいという結論になった場合でも、この場では実装しない。変更に進みたい場合は `/grill-rust` や `/impl-rust` など実装系スキルへの引き継ぎを提案する。

## 論点ごとの出力形式

### 論点: [対象の設計判断]

**現状の設計**: 該当コードの説明。根拠は `ファイル名:行番号`

**推測される意図**: なぜこの設計を選んだと考えられるか。根拠（コード上の制約、依存関係、命名、コミット履歴等）を添える

**メリット**:
- 列挙

**デメリット**:

| デメリット | 分類 | 根拠・補足 |
|---|---|---|
| 欠点の内容 | 解消済み / 運用でカバー / 受容済み負債 / 未対策 | 一次情報（コード・履歴）での確認か推測か |

分類基準（`/survey` と同じ）:
- **解消済み**: 実装上の工夫・補完機構で対策・打ち消しができている、または実質的な影響がほぼない
- **運用でカバー**: コード上の対策はないが、運用ルール・実装方針で許容されている
- **受容済み負債**: 判明している欠点だが、対応コストが移行コストに見合わず現状は受け入れている
- **未対策**: 上記のいずれにも該当せず、対策が確認できない

**他に取り得た設計**:

#### 案A: [名前]
- メリット: ...
- デメリット: ...

#### 案B: [名前]
- メリット: ...
- デメリット: ...

（他に妥当な案があれば追加する）

**採用されなかった理由の推測**: なぜ現状の設計が選ばれ、上記の案が選ばれなかったかの推測。コード・履歴に根拠があれば引用し、なければ「根拠が見当たらず推測」と明示する

**所感**: 上記を踏まえた評価。現状の設計が妥当と考えるならその理由。逆に、いずれかの代替案の方が優れていて採用されていない理由も見当たらない場合は、その旨を明確に指摘し、根拠を添えて提案する

## 完了報告

全論点についてユーザーと合意（または保留の判断）に達したら、議論した論点と結論を簡潔に列挙して締める。ファイルへの保存は行わない（必要であればユーザーから明示的に依頼された場合のみ行う）。
