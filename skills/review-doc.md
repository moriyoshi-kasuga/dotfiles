# ドキュメントレビュー

**対象**: $ARGUMENTS（ファイルパスならRead、URLならWebFetch、未指定なら会話コンテキスト中のドキュメント）

書き直しは行わない（`Skill(review-common)` の基本姿勢も参照）。フィードバックは簡潔かつ実行可能にし、著者の既存の用語・表現は正確に保持する。

## レビュー観点

ドキュメントの種類に応じて選ぶ（技術記事は全観点、仕様書・スキル定義は3〜6のみなど）。

1. **タイトル**（技術記事向け）— 主要キーワードを含み、盛り込みすぎて焦点がぼやけていないか
2. **結論ファースト**（技術記事向け）— 冒頭に結論があるか（PREP法）、ファーストビューで要約が伝わるか
3. **見出し構造・目次** — NotionやZennの自動TOCを前提に見出しだけを上から読む。論理的な流れになっているか、見出しだけで内容が推測できるか、同階層の粒度・表現形式が揃っているか、階層が内容の重要度と一致しているか
4. **流し読みのしやすさ** — 太字だけ拾い読みして大意が掴めるか、箇条書き・図・コードブロックが適切か
5. **前提の明示** — 主題・対象読者・前提知識が伝わるか、見出しと本文の用語が一致しているか
6. **トーン・構造** — 攻撃的な表現、構造上の矛盾・重複がないか

## 出力

`Skill(review-common)` の骨格（良い点 → 改善点 → サマリー）に従う。改善点は `- **[観点] [重要度: 高/中/低]** 場所: 問題 → 改善提案` の形式。重要度は 高=誤解・情報欠落、中=読みにくい・前提不明確、低=表現の改善提案。
