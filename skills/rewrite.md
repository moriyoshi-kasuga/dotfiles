# 完全リライト（Rust）

**対象**: $ARGUMENTS

対象の決め方・フェーズ運用・設計判断ポイントの書式は `rust-coder` スキルの「提案フェーズの共通ルール」に従う。

## 哲学

**「現状をどう直すか」ではなく「この要件に対する最適解は何か」から考える。**

- 既存実装は要件の参考にとどめる。「何を達成したいか」だけを抽出し、実装方法・API・モジュール構成・後方互換性には縛られない。より良い設計のためなら既存の利用箇所が壊れてよい（壊れる箇所は提案時に明示する）
- ただし外から見た機能・振る舞いは維持する。手段はすべて再設計の対象
- 実行時チェック・命名規約・コメントで守っているものは、可能な限り型によるコンパイル時保証に置き換える

## 実行手順

### フェーズ1: rewrite 設計の提案

0. `Skill(rust-coder)` を読み込む
1. **要件の抽出** — 入出力・副作用・エラー条件・利用箇所から「外から見て何を達成しているか」を言語化する。内部構造・アルゴリズム選択は参考にとどめ、要件と切り分ける
2. **既存設計の問題点** — なぜ改善ではなく書き直すべきか、根本的な限界を挙げる
3. **新設計** — ゼロベースで考えた最良の設計を、モジュール分割・型設計・トレイト境界・主要シグネチャで示す。一意に定まる部分は確定案として書く
4. **設計判断ポイント** — 判断が分かれる箇所を列挙する
5. **影響範囲** — 書き直しで壊れる既存の利用箇所を `Grep` で確認して列挙する

### フェーズ2: 完全リライト

6. 採用方針を復唱し、既存実装を捨てて確定した設計で書き直す
7. 破壊的変更で壊れる呼び出し元を、新インターフェースに合わせて修正する
8. `rust-coder` の検証手順で green にする。旧設計に依存して壊れる既存テストは、意図（＝要件）を維持したまま新設計に沿って書き直す

## rewrite 固有の観点

- ライフサイクル・状態遷移があるなら typestate も検討する
- 同期 API か非同期 API かを設計段階で決めて混在させない（ブロッキング処理は `spawn_blocking` に隔離）。共有はロックより所有権・チャネルで設計し、ロックを使うなら `.await` をまたがない粒度に切る
- 既存コメントは一旦白紙で見直し、新設計に対して非自明な WHY だけを残す

## 出力形式

### フェーズ1: 提案

```
## 抽出した要件
## 既存設計の問題点
## 新設計
## 設計判断ポイント
## 破壊的変更
- [変わる API / シグネチャ / モジュール構成]

## 影響範囲（壊れる利用箇所）
- `ファイル名:行番号` — [どう壊れるか・どう追従するか]
```

### フェーズ2: リライト結果

**採用方針** / **書き直したもの** / **追従修正**（修正した利用箇所） / **検証結果** / **要確認**（自動検証で担保できない確認事項。実行時の挙動・外部システム連携など。なければ「なし」）
